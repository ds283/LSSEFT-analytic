# Campaign: pre-Python-migration fixes to `LSSEFT-analytic`

## Why this campaign exists

`LSSEFT-analytic` is to be ported to Python + SymPy. The feasibility study
(`~/Documents/Code/ScaleDependentBias/documents/python-migration/LSSEFT-analytic-feasibility.md`)
concludes that the port is feasible **because the C++ can be rebuilt and run as a differential
oracle at every step**, and that the highest-return work available right now is therefore to
*repair the oracle first* (study §9, "Phase −1" and "Phase 0").

An oracle with known defects is a bad oracle: you either replicate its bugs in the port to make
the diffs pass, or you cannot tell a port error from an oracle error. Several of the fixes below
convert *silently wrong* into *loudly stops*, which is exactly the property an oracle needs.

This campaign implements Phase −1 and Phase 0. It adds no new physics capability and changes no
published number. Its success criterion is: **the same 101 kernels and 135 assembly functions,
produced reproducibly, from a build that needs only a C++17 compiler and `pkg-config ginac`, with
the latent defects removed and the remaining uncertainties written down.**

## Read this first

`RECONCILIATION.md`, in this directory, records exactly which of the study's claims were verified
against the code, which were corrected, and what was newly discovered during planning. **Every
prompt assumes you have read it.** In particular it contains three things you will otherwise waste
hours rediscovering:

1. **There is no working binary today.** Boost is not installed on this machine and the two
   committed binaries are the wrong architecture. Prompt 01 is a hard precondition for everything
   else.
2. **GiNaC 1.8.10 randomises expression ordering per process.** Two runs of the same binary with
   the same flags produce different `autogenerated/` trees. The content is identical; the naming
   and ordering are not. This is why the regression test is functional rather than textual, and it
   is the subject of prompt 03.
3. **The study's account of *why* ordering is non-deterministic is wrong** (it blames
   `std::less<GiNaC::symbol>`, which is in fact already name-ordered). The real chain is
   printed-string hashes → `std::unordered_map` bucket order → kernel naming and emission order.

### Recommended ordering

**01 → 02 → 03 → 04 → 05 → 06 → 07**, strictly sequential.

The ordering is not arbitrary:

- **01 before everything** because there is no build otherwise. The study puts "delete Boost" first
  for the same reason: it reduces the oracle's build requirements to a compiler and `pkg-config`,
  which is what makes it runnable in CI and by an agent without a package-manager step.
- **02 before 03** because you must capture the *pre-fix* behaviour before you start changing it,
  and because the harness is the acceptance test for everything after it. The study: "Nothing else
  is safe without it, because the code has no tests."
- **03 before 04/05/06** because until emission order is deterministic, a diff of the generated
  tree is unreadable and every later change has to be validated the slow way. The study calls this
  "a prerequisite for diff-based validation", and the measurements in `RECONCILIATION.md` §3 show
  it is worse than the study thought: *identical runs* disagree.
- **04, 05, 06 in any order among themselves**, but sequentially, so each lands against a clean
  baseline and each commit is independently revertible. 04 first because it is the only one of the
  three that is expected to change internal behaviour (it activates 678 previously-dead branches),
  so it deserves the freshest baseline and the most attention. 06 last because its outcome may be
  "no code change, a findings document" and it must not block the others.
- **07 last**, to re-archive and tag against the final state.

### Dependency notes that are easy to get wrong

- **04 must be landed as one commit.** Fixes (ii) and (iii) mutually mask each other. Applying (ii)
  without (iii) truncates 678 Wick products and produces silently wrong physics. The prompt says
  this too; it is repeated here because it is the single most dangerous item in the campaign.
- **05's Legendre work must not weaken any existing throw.** The three sites currently fall through
  silently on shapes they do not understand. They must end up *raising*, never guessing.
- **06 must not re-enable the commented-out throw as written.** The study measured it firing 128
  times on a working run. Diagnose first; assert the invariant that actually holds, if one does.
- **03's byte-reproducibility goal may not be fully attainable.** GiNaC's per-process ordering is
  outside our control. The prompt asks for a measurement and an honest record of the residue, not
  a promise.

## Working agreements for every prompt

### Baseline and verification

The reference for "did I break anything?" is **functional equality of the emitted integrands**, not
textual equality:

- the multiset of (integrand × Wick product) signature vectors, evaluated at a fixed set of random
  `(k, q, z)` points with a surrogate `P(k)`, must be unchanged;
- the set of `compute_*` function names must be unchanged;
- the counterterm map must be unchanged after canonicalisation;
- the set of emitted warnings must be unchanged.

Prompt 02 builds the tooling for this and archives the baseline it compares against. Prompts 03-07
run it. If a prompt *intends* to change one of these, it says so explicitly and the log must record
the before/after.

The canonical invocation, matching the 2018 published output, is:

```bash
./LSSEFT_analytic --no-auto-symmetrize --symmetrize-22 --counterterms --output <dir>
```

Note that this is **not** the default. `--auto-symmetrize` is the default and costs 26× for
identical results.

### Commits

Commit **once** at the end of each prompt, on a branch, never directly on `master` unless the user
has said otherwise. Standard format:

```
<imperative subject, <= 72 chars, no trailing period>

<blank line>
- what changed, one bullet per coherent change
- why, where the reason is not obvious from the change
- what was verified, with the actual numbers

Refs: prompts/pre-python-migration-fixes/NN-<slug>.md

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

One prompt, one commit. This gives a clean sequence of rollback points tied 1:1 to the prompts.
If a prompt genuinely cannot be done in one commit, say so in the log and explain the split.

### Logs

Every prompt writes `prompts/pre-python-migration-fixes/logs/NN-<slug>.md` using
`logs/TEMPLATE.md`. The log exists so that a later agent or human can understand what was done
**without re-deriving it from the code**. It must be detailed enough that, wherever the shipped
code differs from the prompt, a reader can tell which of these three it is:

| Classification | Meaning | What the log must contain |
|---|---|---|
| **Structurally required** | The prompt's instruction could not be followed as written; the code, the language or a dependency forced a different shape. | What was attempted, the concrete obstacle (compiler error, API shape, measured behaviour), and why the chosen alternative is the minimal one. |
| **Implementation choice** | Several workable options existed and one was picked. | The options considered, the criterion used, and enough of the trade-off that a later reader can *disagree on the merits* rather than just wonder. |
| **Unintended drift** | The change was not asked for and not forced. | Say so plainly. Do not quietly normalise it. If it is harmless, say why it was kept; if it should be reverted, say that. |

Silence is not an option: a difference between prompt and code that the log does not classify is
itself a defect in the log.

### Status board

Every prompt updates `IMPLEMENTATION_STATE.md` in this directory — at the **start** (mark the
prompt in flight) and at the **end** (mark complete, record the commit SHA, record any issue it
opened or closed). That file is the single place to look to find out where the campaign is.

### Scope discipline

`RECONCILIATION.md` §6 lists what is deliberately out of scope. If you find yourself wanting to fix
the dedup key, restructure the bias filters, rewrite `is_IR_safe`, or add a `Bk` placeholder —
stop, and record it as an open item in `IMPLEMENTATION_STATE.md` instead. Those belong to the
Python port, and doing them here would make the oracle diverge from the artefact it is supposed to
validate against.
