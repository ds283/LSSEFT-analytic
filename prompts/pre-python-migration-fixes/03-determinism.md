# Prompt 03 — Deterministic kernel naming and emission order

You are working in `~/Documents/Code/LSSEFT-analytic`. **Read**
`prompts/pre-python-migration-fixes/README.md`, `RECONCILIATION.md` (especially §3),
`validation/NONDETERMINISM.md`, and `logs/02-oracle-harness-and-baseline.md` first.

## Objective

Make the generated `autogenerated/` tree reproducible: the same source, the same flags and the same
GiNaC must produce the same kernel numbering and the same file ordering on every run.

The study (§4.2, §9 item 2) calls this a prerequisite for diff-based validation. The measurements
in `RECONCILIATION.md` §3 show it is more urgent than the study realised: *identical runs of one
binary* currently disagree on 10 of 22 generated files, and the counterterm map varies too.

## Why this matters and what it is worth

Every prompt after this one, and every stage of the Python port, validates by diffing. Right now a
diff is unreadable: kernel `ker38` in one run is a different kernel in the next. Fixing this turns
the whole generated tree into a reviewable artefact and makes a regression a `git diff` instead of
a numerical hunt.

## Preconditions

- Prompts 01 and 02 complete; `baseline/pre-fix` tag exists.
- Working tree clean. New branch.

## The causal chain (already established — do not re-derive)

From `RECONCILIATION.md` §3.2, verified by reading:

1. GiNaC 1.8.10 seeds its expression hash from a runtime address, so `mul`/`add` operand ordering
   and hence the **default-printed form** of an expression differ between processes. This is a
   GiNaC behaviour and cannot be switched off from outside the library.
2. `one_loop_element_key::hash()` — `lib/one_loop_reduced_integral.cpp:372-414` — hashes the
   default-printed strings of the time function, measure and Wick product.
3. `LSSEFT_impl::LSSEFT_kernel::hash()` — `backends/LSSEFT.cpp:89-121` — hashes the default-printed
   string of `(measure*integrand).expand()`.
4. Those hashes key two `std::unordered_map`s:
   - `one_loop_element_db` — `lib/one_loop_reduced_integral.h:211`
   - `LSSEFT::kernel_db` — `backends/LSSEFT.h:172`
   and a third in the same family, `Pk_one_loop_impl::Pk_db` — `lib/Pk_one_loop.h:62`.
5. `Pk_rsd_group::visit` — `lib/Pk_rsd.h:176-181` — walks `one_loop_element_db` in bucket order and
   hands elements to `LSSEFT::process_kernels` — `backends/LSSEFT.cpp:498-520` — which assigns
   `ker0, ker1, …` **in that order** via `make_unique_kernel_name()` (`backends/LSSEFT.cpp:492`).
6. Every emission loop then walks `kernel_db` in bucket order. The sites are
   `backends/LSSEFT.cpp:633, 684, 783, 798, 814, 841, 860, 878, 905, 932, 953, 964, 987, 1269, 1290`.

**Equality is not affected.** `LSSEFT_kernel::is_equal` (`backends/LSSEFT.cpp:58-86`) uses GiNaC
structural equality, which is order-insensitive, so deduplication is already correct. Only ordering
and naming move. Do not "fix" the equality test.

Two other ordering sites to check while you are here:

- `Pk_rsd_group::get_time_functions()` — `lib/Pk_rsd.cpp:129-154` — builds a `std::vector` by
  walking the same unordered dbs; that vector's order reaches `Pk_expressions.cpp`.
- `loop_integral::canonicalize_Rayleigh_labels()` — `lib/loop_integral.cpp:144-166` — iterates a
  `GiNaC::exmap`, i.e. `std::map<ex, ex, ex_is_less>`, which orders by `ex::compare()` and is
  therefore type/serial dependent rather than name dependent. Its sibling
  `canonicalize_loop_labels()` (`:114`) iterates a `GiNaC_symbol_set` and **is** name-ordered, so
  it is already fine. Note the asymmetry; decide whether it matters and record the decision.

Note the study's own account of the cause is wrong: it blames `std::less<GiNaC::symbol>` for
ordering by serial number, but `utilities/GiNaC_utils.h:39-51` specialises it to order lexically by
name. `GiNaC_symbol_set` is already deterministic. Do not spend time there.

## The approach

Do **not** change container types wholesale, and do not try to make GiNaC's own comparator
deterministic. Instead:

### Step 1 — a canonical, print-order-independent signature

Add a small utility (suggested: `utilities/canonical_print.{h,cpp}`) providing

```cpp
std::string canonical_string(const GiNaC::ex& e);
```

with these rules, applied recursively:

| Node | Rendering |
|---|---|
| `numeric` | its default print (rationals print canonically and are stable) |
| `symbol` | `get_name()` |
| `constant` | its name |
| `function` | `name(` + canonical of each argument, **in argument order** + `)` — argument order is semantic, do not sort it |
| `power` | `(` + canonical(base) + `)^(` + canonical(exponent) + `)` |
| `add` | canonical of each operand, **sorted lexicographically**, joined with `+`, wrapped in `[...]` |
| `mul` | canonical of each operand, **sorted lexicographically**, joined with `*`, wrapped in `{...}` |
| anything else | default print, and record in the log that you hit it |

The sorting of `add`/`mul` operands is the whole point: it removes GiNaC's process-random ordering
from the key. This function is a *sort key and hash input*, not a pretty-printer — it does not have
to be re-parseable, only stable and injective enough to order by.

Guard against the "anything else" branch silently absorbing something important: at minimum log or
assert on unexpected node classes during development, and report what appeared in a full run.

### Step 2 — use it for the hashes

Replace the `std::ostringstream expr_string; expr_string << combined;` pattern with
`canonical_string(combined)` in:

- `one_loop_element_key::hash()` — `lib/one_loop_reduced_integral.cpp:372-414` (three sites: time
  function, measure, Wick product)
- `LSSEFT_kernel::hash()` — `backends/LSSEFT.cpp:89-121` (one site)

This alone makes bucket assignment stable across processes. It does **not** by itself make
iteration order stable, because `unordered_map` iteration order also depends on insertion order and
rehash history — so do step 3 as well, and do not stop at step 2 because a couple of runs happened
to agree.

### Step 3 — impose a total order at every point where order is observable

The robust and reviewable fix is to sort once, name from the sorted order, and iterate the sorted
sequence everywhere.

- Give `LSSEFT` an ordered view of its kernels — for example build, after all kernels are
  registered, a `std::vector<std::pair<const LSSEFT_kernel*, std::string>>` sorted by the tuple
  `(canonical_string(measure*integrand expanded), canonical_string(WickProduct),
  joined integration-variable names, joined external-momentum names)`. Replace all fifteen
  `for(const auto& record : this->kernel_db)` loops with iteration over that vector.
- Assign `kerN` names **from the sorted order**, not from insertion order. That means
  `process_kernels` (`backends/LSSEFT.cpp:498-520`) should collect kernels without naming them, and
  naming should happen once in `write()` (or a new `finalize()` called from it) after sorting.
  This is the change with the largest blast radius — `kernel_db` maps kernel → name and
  `LSSEFT::print_Pk_expression` reads names back out at `:1193` and `:1217`. Plan it before you
  start editing.
- Sort `Pk_rsd_group::visit`'s traversal of each `one_loop_element_db` by the same canonical key,
  so that the order in which elements reach `process_kernels` is stable regardless.
- Sort `Pk_rsd_group::get_time_functions()`'s output by `canonical_string` of each time function.
- Decide about `canonicalize_Rayleigh_labels()`. If it can be made name-ordered without changing
  results, do it; if changing it moves the emitted kernels, **stop and do not change it** — record
  why in the log, because that would be a behaviour change disguised as a determinism fix.

### Step 4 — the counterterm map

`main.cpp:158-181` (`write_map`) prints the counterterm map from `Pk_rsd_set` and
`Pk_rsd_group::get_UV_limit` (`lib/Pk_rsd.cpp:91-116`), which sums over unordered dbs.

Two separate problems, and you should treat them separately:

- **Line order** is ours and is fixable: sort the emitted lines within each group before printing,
  or iterate a sorted view.
- **Factor order inside each printed expression** is GiNaC's and is process-random (this is issue
  I-01). Sorting lines does not fix it. Options: leave it and have the comparison canonicalise; or
  route the counterterm map through a deterministic printer. The first is cheap and honest; the
  second is more work and changes human-readable output.

Pick one, **and record the choice with its reasoning** — a later reader must be able to disagree on
the merits. If you leave it, make sure `validation/` has a canonicalising comparison for the
counterterm map and that `NONDETERMINISM.md` records the residue precisely.

## Explicit non-goals

- Do **not** change what is emitted, only its order and its names. Kernel *content* must be
  bit-identical to the pre-fix baseline as a set.
- Do **not** change the dedup key from expanded-form to rational normal form. That would merge the
  six duplicate pairs (issue I-05) and is out of scope for this campaign.
- Do **not** replace `std::unordered_map` with `std::map` keyed on GiNaC's own comparator — GiNaC's
  cross-type comparison is exactly the thing that is not stable.
- Do **not** try to pin GiNaC's hash seed.

## A note on the timestamp

`backends/LSSEFT.cpp:619` and `:1534` write a generation timestamp into `pipeline_id()` and into
every generated file header. Byte-comparison across runs must exclude those. **Do not** make the
timestamp fixed by default: `pipeline_id()` is a downstream identity string for the `LSSEFT`
database and each generation run is meant to be distinguishable.

If you want a `SOURCE_DATE_EPOCH`-style override for CI, that is defensible — but it is an
implementation choice with cross-repository consequences, so implement it *off by default* and
argue for it in the log, or leave it out and say you considered it.

The acceptance test is a measurement, not an assumption. GiNaC's per-process ordering may leak into
printed expressions in ways sorting cannot reach; find out how far you got and say so honestly.

1. **Five independent runs**, same binary, same flags, into five directories. For each of the 22
   generated files, compute md5 **after stripping the `// Generated at …` line** and excluding
   `pipeline_id.cpp`. Target: all five identical, for all files.
2. If any file still varies, identify exactly which and why, at expression granularity. Do not
   round the result off. Record it under issue I-01 with the specific construct responsible.
3. **Toggle `--counterterms`.** With `--no-counterterms`, the code-generation output should be
   *identical* to the `--counterterms` run (toggling it should not affect code generation at all —
   the study flags that it currently does). Verify; if it still differs, that is a finding worth a
   new issue.
4. **Functional equality with `baseline/pre-fix`** via `validation/compare_autogenerated.py`:
   identical signature multiset, identical `compute_*` name set, identical warning set. Kernel
   *numbering* is expected to change — that is the point — so the comparison must be the
   renumbering-insensitive one.
5. **Counterterm map** equal to the baseline after whatever canonicalisation you settled on.
6. Wall clock still ≈ 43 s. `canonical_string` is called O(#kernels) times on expanded expressions;
   if you see a large regression, you are calling it in an inner loop. Report the actual number.
7. Re-run the 2018 comparison (`~/Documents/Code/LSSEFT/autogenerated/`) — still a functional match.
