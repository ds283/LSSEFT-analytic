## 3. Divergences from the prompt

### 3.1 Structurally required

> **D-1 — three commits, not one, and the smoke test necessarily runs after the tag**
> **Prompt asked:** Process step 4, "One commit, then the tag" (exact template given), followed by
> Verification item 3, the clean-checkout smoke test "at the tagged commit" and Log requirement
> "the clean-checkout smoke test: exact commands, exact result" — i.e. the log itself must contain
> a result that can only be produced by building the state the tag points to.
> **Shipped:** three commits. (1) The substantive commit, matching the prompt's template exactly
> (`<N>` filled with `11`, the count of bullets in `validation/ORACLE.md` §5), containing every
> deliverable except its own SHA and the smoke-test result. (2) A bookkeeping commit filling that SHA
> into this log and into `IMPLEMENTATION_STATE.md` — the same pattern every one of prompts 01-06 used,
> for the identical reason (a commit's message cannot contain its own hash). (3) The tag
> `baseline/post-fix` is placed on commit (2), per the precedent set by prompt 02 (`logs/
> 02-oracle-harness-and-baseline.md`'s own header note: "the tagged code and archived baseline are
> exactly those of [the substantive commit], whose tree differs from the first only in [documentation
> files]"). The clean-checkout smoke test was then run for real against that tag — a `git worktree
> add` at `baseline/post-fix` itself, not at an argued-equivalent ancestor — and its result appended
> in a third, small commit that touches only this log (no source, no baseline content, no board entry
> beyond a pointer).
> **Obstacle:** two independent instances of the same fact. First, a commit cannot record its own
> SHA (needed to fill "Commit:" above). Second, and specific to this prompt: the smoke test's whole
> point is to prove that a build from the *tagged* commit reproduces the baseline, and the tag cannot
> exist before the commit it tags, so the log entry proving this can only be written after the tag —
> at which point the commit that would need to carry it is already made.
> **Why this is minimal:** prompt 07 changes no program source file at all (confirmed: `git diff
> --stat` against every source directory — `lib/`, `SPT/`, `backends/`, `services/`, `utilities/`,
> `shared/`, `main.cpp`, `CMakeLists.txt`, `cmake/` — is empty for the whole of this prompt's work, see
> §4). The third commit therefore cannot itself have invalidated anything the smoke test measured; it
> only adds prose to a log file. No smaller number of commits was found that both (a) lets `git tag`
> point at a real, already-tested state and (b) lets the log genuinely report that test's result
> rather than a prediction of it.

### 3.2 Implementation choices

> **D-2 — the "47 value_ expressions differ" count was established by matching kernels on their
> Wick_ text, not on kerNNN name**
> **Prompt asked:** "confirm the count and confirm the sorted Wick_ set is unchanged" for the
> post-fix vs pre-fix textual comparison, without specifying a matching method (kernel numbering is
> permuted between the two trees, so a naive `kerN` vs `kerN` diff would be meaningless).
> **Shipped:** a small ad-hoc script (not committed — see §4) that extracts every kernel's `(value_,
> Wick_)` pair from both trees via `validation/canonical_form.py`'s own `extract_kernels`, groups by
> `Wick_` text (confirmed unique enough to be a matching key on this basis: the sorted `Wick_` line
> multiset is byte-identical between the two trees, `md5 c5e5f54e10c05cb0da704b8347cabafb` both
> sides), and for each `Wick_` group compares the multiset of `value_` strings on each side.
> **Options considered:** (a) match by the functional signature vector already computed by
> `compare_autogenerated.py` (would require extending that script to report per-kernel pairing
> rather than only a match/mismatch multiset verdict); (b) match by `Wick_` text (shipped); (c) match
> by `canonical_form.py`'s existing `canonical_key()` used for dedup (also viable, but does more work
> than needed — it further reduces `value_` via `cancel(together(·))`, which would hide the very
 information the comparison is meant to surface). **Criterion used:** (b) needed no change to any
committed tool, ran in seconds, and its correctness rests on a fact independently verified in the
same step (the `Wick_` multiset is unchanged, so grouping by it cannot merge two kernels that
"shouldn't" be compared together). **Trade-off a later reader might weigh differently:** this method
(implemented as a throwaway script under the session scratchpad, not committed) would over-count if
two kernels legitimately shared identical `Wick_` text before the FabJ change but had different
`value_` for an unrelated reason — this was checked not to be the case here (the residual mismatch
count came out exactly 47 on both the "unmatched in A" and "unmatched in B" sides, consistent with a
clean bijection within the one affected `Wick_` group, not a partial/ambiguous match), but a
committed, permanent version of this comparison would be a reasonable thing for the port's own
tooling to formalise rather than reimplement each time this question comes up.

## 8. Notes for whoever comes next

- **Every measurement in this log was taken from a tree that differs from `74bc284` (this prompt's
  own parent commit) only in `validation/` and `prompts/`.** If you are trying to reconcile a number
  here against the source, you are looking at exactly the same `lib/`, `SPT/`, `backends/`,
  `services/`, `utilities/`, `shared/`, `main.cpp` as prompt 06 left them.
- **The `Wick_`-grouped matching method used to confirm "47" (§3.2 D-2) is a one-off, not a permanent
  tool.** If the port's own tooling needs "which specific kernels changed between two trees with
  permuted numbering" as a recurring question (rather than the multiset match/no-match verdict
  `compare_autogenerated.py` already gives), it would be worth promoting this into
  `validation/canonical_form.py` properly rather than reimplementing it from a throwaway script each
  time, as this log did.
- **The three-commit structure (§3.1 D-1) is not a shortcut around "one commit, then the tag"** — it
  is the same constraint that produced 01-06's two-commit pattern, plus one further, prompt-07-specific
  turn of the same screw (the smoke test needs the tag to exist, and the tag needs a commit to exist).
  A future close-out prompt in a similar campaign should expect the same shape and not be surprised by
  it.
- **Dead end avoided:** an early attempt to confirm the "47" count by diffing sorted `kerNNN: value_`
  lines directly (i.e. comparing line N of one sorted file against line N of the other) produced a
  meaningless number, because sorting the `double value_ = ...;` lines textually does **not** put the
  "same" kernel (by content) at the same position once 47 of 101 expressions have a different printed
  term order — two kernels with unrelated content can sort adjacently to each other by coincidence of
  their leading characters. The `Wick_`-grouped method (§3.2 D-2) was adopted specifically because it
  does not depend on any sort order at all.
