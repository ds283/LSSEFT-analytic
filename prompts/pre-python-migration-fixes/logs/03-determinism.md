## 1. What this prompt was for

`LSSEFT-analytic` emits a 22-file `autogenerated/` C++ tree from a symbolic GiNaC computation.
GiNaC 1.8.10 seeds its expression hash from a per-process value, so two runs of the identical
binary with identical flags previously produced different kernel numbering (`ker0`, `ker1`, ...)
and different file ordering, even though the underlying integrand *content* was already
byte-stable (prompt 02's finding, `validation/NONDETERMINISM.md`). This prompt makes kernel naming
and emission order deterministic by sorting on a print-order-independent canonical key instead of
trusting `unordered_map` bucket order (itself downstream of GiNaC's per-process hash), so that the
generated tree becomes a reviewable, diffable artefact for every later prompt in the campaign.

## 3. Divergences from the prompt

### 3.1 Structurally required

None. The prompt's approach (a canonical string utility; use it in the two hash functions; sort
and name from a total order; sort the two named traversal sites; leave `is_equal`/the dedup key/the
container types/the hash seed alone) was followed exactly as specified, and nothing in the codebase
forced a different shape.

### 3.2 Implementation choices

> **D-1 — `canonical_string()`'s fallback branch, and what actually exercises it**
> **Prompt asked:** a table of rules for `numeric`/`symbol`/`constant`/`function`/`power`/`add`/`mul`,
> plus "anything else: default print, and record in the log that you hit it", with an instruction
> to "log or assert on unexpected node classes during development, and report what appeared in a
> full run."
> **Shipped:** exactly that table, plus a fallback that GiNaC-default-prints the node and writes a
> one-line `std::cerr` warning the *first* time each distinct class name is seen (a `static
> std::set<std::string>` dedups repeats, so a full run cannot flood stderr).
> **What appeared in a full run:** nothing. `grep -l "unhandled GiNaC" <every run log>` returned no
> matches across all five determinism-check runs, the `--counterterms`/`--no-counterterms` pair,
> and the 2018-comparison run. The values the two hash functions canonicalise
> (`one_loop_element_key::hash()`'s time function/measure/Wick product, and
> `LSSEFT_kernel::hash()`'s `measure*integrand`, all `.expand()`-ed first) apparently reduce, after
> dimensional reduction, to nothing but `numeric`, `symbol`, `constant` (`Pi`), `power`, `add`,
> `mul` and `function` (`Pk`, `D`, `DA`, ..., and the special functions in
> `backends/LSSEFT.cpp`'s `func_convert` table) — even though `LSSEFT_kernel::print_integrand`'s
> `format_print` defensively special-cases `tensdelta`/`idx`/`varidx`/`indexed` for the *emitted*
> C++ text, none of those apparently reach the *hash* inputs in the canonical run. This is
> reported, not assumed.
> **Why this is the right shape:** it satisfies the prompt's instruction precisely, and the
> zero-hits result is itself useful evidence: it means the seven-rule table is complete for this
> codebase's actual expressions, not merely complete on paper.

> **D-2 — the 15 emission-loop edits add a line rather than rewriting the loop body**
> **Prompt asked:** "Replace all fifteen `for(const auto& record : this->kernel_db)` loops with
> iteration over that vector."
> **Shipped:** `for(const auto& record_ref : this->ordered_kernels) { const auto& record =
> record_ref.get(); ... }` — i.e. the loop header changes, and one line is added at the top of the
> body to rebind the name `record` to what it always was (a `const kernel_db_type::value_type&`),
> leaving every other line of all 15 bodies (some of which are 15-20 lines of `outf <<` statements)
> completely unedited.
> **Options considered:** (a) rewrite every `record.first`/`record.second` in all 15 bodies to
> `record_ref.get().first`/`.get().second`; (b) make `ordered_kernels` a
> `std::vector<const kernel_db_type::value_type*>` and rewrite every `record.first` to
> `record->first`; (c) the shipped one-line rebind.
> **Criterion used:** (a) and (b) both touch on the order of a hundred call sites across 15
> functions for a purely mechanical reason, which is exactly the kind of large, low-information
> diff the prompt's own rationale for this prompt (turning the generated tree into "a reviewable
> artefact") argues against inflicting on the *source* diff. (c) makes each of the 15 diffs a
> two-line, obviously-correct change (new loop header, one new binding line) with the body a pure
> context line, so a reviewer can check "was any loop missed" (§ the prompt's own requirement) by
> `grep`-ing for `this->kernel_db` in a `for` position, which now returns only the three
> non-iteration sites (`process_kernels`'s `find`/`insert` and the two `.at(ker)` lookups).
> **Trade-off a later reader might weigh differently:** the `record_ref`/`record` naming is one
> extra local per loop that a reader has to see through; a reader who dislikes that can inline
> `record_ref.get()` directly, at the cost of a much larger diff against every body.

> **D-3 — naming deferred to `write()`, which changes its signature from `const` to non-`const`**
> **Prompt asked:** "`process_kernels` should collect kernels without naming them, and naming
> should happen once in `write()` (or a new `finalize()` called from it) after sorting."
> **Shipped:** exactly that, via `LSSEFT::finalize_kernel_names()` (idempotent, guarded by a
> `kernels_finalized` flag) called as the first statement of `write()`. Since
> `finalize_kernel_names()` mutates `kernel_db` (writing the assigned name into each entry) and
> `ordered_kernels`, and `write()` was previously `const`, `write()`'s declaration had to change
> from `void write() const;` to `void write();`.
> **Options considered:** (a) drop `const` from `write()` (shipped); (b) mark `kernel_db`,
> `ordered_kernels`, `kernel_count` and `kernels_finalized` `mutable` and keep `write() const`; (c)
> do the sort/naming step inside `add()` instead, on every call, guarded to run only once all
> kernels are known — but `LSSEFT` has no way to know when the *last* `add()` call happens (`main.cpp`
> calls `add()` exactly once with the whole `Pk_rsd_set`, but nothing in the class enforces that).
> **Criterion used:** `write()` is called exactly once, immediately after `add()`, from a
> non-`const` local (`backend.write();` in `main.cpp`) — there is no caller anywhere that needs
> `write()` to stay `const`. Making `write()` non-`const` is a one-line, self-documenting change
> ("this method now mutates state") versus marking four unrelated members `mutable`, which would
> silently permit mutation from *any* `const` method, not just the one that is supposed to do it.
> (c) was rejected because it invents a "last add() call" contract the class cannot check.
> **Trade-off a later reader might weigh differently:** any future caller that genuinely needs to
> call `write()` through a `const LSSEFT&` would now have to work around it (e.g. `const_cast`).
> No such caller exists today.

> **D-4 — `canonicalize_Rayleigh_labels()` left untouched, as an implementation choice**
> **Prompt asked:** "If it can be made name-ordered without changing results, do it; if changing it
> moves the emitted kernels, stop and do not change it — record why."
> **Shipped:** no code change; a documentation comment was added above the method (see §2) pointing
> here.
> **Reasoning:** `canonicalize_Rayleigh_labels()` iterates `this->Rayleigh_momenta`, a
> `GiNaC::exmap` (`std::map<ex,ex,ex_is_less>`) ordered by `ex::compare()`, and assigns the *label*
> `R0`, `R1`, ... to each Rayleigh momentum in that iteration order. Unlike a kernel's name (which
> is metadata attached to a dedup key, invisible to the physics), this label is substituted
> directly into the kernel's algebraic content via `this->K.subs(relabel)` and
> `this->WickProduct.subs(relabel)` two lines later — so re-ordering this traversal to be
> name-based would risk swapping *which* physical momentum a given kernel calls `R0` versus `R1`,
> which is a content change dressed as a determinism fix, and the prompt's non-goals explicitly
> forbid changing kernel content. It is also empirically unnecessary: the sorted `value_`/`Wick_`
> line sets — which embed these `R0`/`R1`/... labels as literal C++ symbol names in the emitted
> code — were already byte-identical across all five prompt-02 runs (`772fdcf3...`, `c5e5f54e...`),
> *before* this prompt touched anything, and remain byte-identical (same two md5s, reproduced
> exactly — see §4) after every other change in this prompt landed. That is direct evidence that
> whichever order `this->Rayleigh_momenta`'s `ex::compare()` actually produces is already
> process-stable in practice for this codebase: the Rayleigh momenta reaching this point are
> created by deterministic, non-hash-driven C++ control flow (explicit loop counts and function
> calls), not by iterating an unordered container, so `ex::compare()`'s tie-breaking (which for
> `GiNaC::symbol` objects of the same type is documented to fall back to a construction-order
> serial number, not to a runtime-address-seeded hash) never actually has to arbitrate between
> hash-random orderings here. Given that, "make it name-ordered" would trade a working, verified
> invariant for a change that risks moving kernel content, for no measured benefit — the textbook
> case the prompt's own "record why" clause is for.
> **Trade-off a later reader might weigh differently:** the asymmetry with `canonicalize_loop_labels()`
> (which *is* name-ordered, via `GiNaC_symbol_set`) remains in the code and could look like an
> oversight to a future reader who has not seen this reasoning — which is why the comment was added
> at the call site itself, not only in this log.

> **D-5 — the counterterm map: line order fixed, intra-line GiNaC print order left to a
> canonicalising comparison, not a canonicalising printer**
> **Prompt asked:** "Line order is ours and is fixable... Factor order inside each printed
> expression is GiNaC's and is process-random... Pick one [leave it and canonicalise the
> comparison, or route through a deterministic printer], and record the choice with its reasoning."
> **Shipped:** line order was fixed as a side effect of D-nothing-new — investigation showed the
> counterterm map's line order was *already* fully deterministic before this prompt touched
> anything (see below), so the only remaining lever, `Pk_rsd_group::get_time_functions()`, was
> sorted anyway per the prompt's explicit instruction (D of §2) even though it currently feeds no
> live output path. The intra-line factor order was left alone; `validation/canonical_form.py
> --counterterm-map` (built in prompt 02) remains the comparison used to gate it.
> **Investigation, because "line order is ours and is fixable" turned out to need unpacking:** the
> `** COUNTERTERM MAP` section printed under `--counterterms` (`main.cpp:508-518`) is built purely
> from `mixing_divergences`/`stochastic_divergences`, i.e. `generate_UV_limit()`
> (`main.cpp:47-70`), whose only unordered-container-driven ingredient is
> `group.get_UV_limit(...)` — a GiNaC *sum* (`+=`) over each `one_loop_element_db`, which is
> commutative, so its insertion order cannot affect the resulting `ex`'s structural content (only,
> potentially, which internal term order GiNaC's own hash-based canonicalisation settles on when
> the sum is later printed — the intra-line issue, unrelated to insertion order). Every other loop
> in `generate_UV_limit`/`generate_map`/`write_map` is a fixed numeric range (mu powers, k powers)
> or an iteration over `Pk_rsd_set` (a `std::map<std::string, ...>`, already name-ordered) — none
> of it depends on `unordered_map` bucket order. `get_time_functions()` — the one genuinely
> unordered-traversal-driven ingredient of the *other* map generator, `generate_map()` — is **not**
> in this call chain: `mixing_map`/`stochastic_map` (which call `generate_map`, which calls
> `get_time_functions()`) are defined in `main.cpp` but never invoked from `main()`. So the printed
> counterterm map's line *order* was already deterministic pre-prompt-03, for reasons unrelated to
> anything this prompt changes — which is confirmed empirically (see §4, the raw sorted-lines
> counterterm-map md5 pattern is unaffected by this prompt, and the *label* multiset was already
> stable at prompt 02).
> **Reasoning for the intra-line decision:** building a canonicalising *printer* (replacing GiNaC's
> own `operator<<` for these expressions with something whose `add`/`mul` term order is fixed
> independently of GiNaC's hash) is a materially larger, riskier change than this prompt's approach
> everywhere else — it would mean re-implementing enough of a GiNaC pretty-printer to cover
> whatever operator/function vocabulary appears in a counterterm-map line, is exactly the kind of
> printer rewrite `RECONCILIATION.md` and the prompt both flag as out of scope/high-risk, and would
> change *human-readable* console output that has existed unchanged since 2017 for a diagnostic
> purpose (a person reading `** COUNTERTERM MAP` to sanity-check a physics result), not an emitted
> artefact anything downstream parses. Prompt 02 had already built exactly the "canonicalise the
> comparison" alternative (`validation/canonical_form.py --counterterm-map`) and shown it collapses
> six independent processes (five runs plus `--auto-symmetrize`) to one md5 — i.e. it already
> demonstrates the map's *content* is verifiably stable; only its *raw bytes* are not. Given a
> working, cheap, already-built alternative that fully discharges the actual regression-testing
> need, and no evidence anything downstream needs byte-stable raw text, the cheaper and lower-risk
> option was kept, exactly as prompt 02's log recommended it should be measured, not assumed.
> **Options considered:** (a) route the counterterm map's `-> mu^N = <expr>` lines through a custom
> canonicalising printer built on top of `canonical_string()`'s traversal (shipped in spirit for
> the *hash* inputs, but not for this *human-readable diagnostic* output); (b) leave it and rely on
> the existing canonicalising comparison (shipped).
> **Criterion used:** cost/risk versus benefit, given that (b) was already built, already verified
> sufficient (prompt 02), and the map is a console diagnostic, not a parsed artefact.
> **Trade-off a later reader might weigh differently:** a reader who wants `git diff`-able
> counterterm-map *console output* (as opposed to a script-mediated comparison) would need option
> (a). Nothing about this prompt's changes makes that harder to add later; it would layer on top of
> `canonical_string()`'s existing traversal.

## 5. Behaviour that intentionally changed

Kernel *naming* and emission *order* changed, exactly as the prompt intends. Before this prompt,
`ker0`..`ker100` were assigned in `unordered_map` bucket order (a function of GiNaC's per-process
hash seed), so the same physical kernel could be `ker38` in one run and `ker71` in the next, and
the order of blocks within all 10 kernel-referencing files moved accordingly. After this prompt,
names are assigned once, from a full sort on `canonical_key()`, so a given kernel's content
determines its name and position deterministically and reproducibly — verified in §4 to be
byte-identical across five independent runs. Kernel *content* did not change: the sorted
`value_`/`Wick_`/`compute_*`/`ker` name-set md5s are identical, digit for digit, to
`baseline/pre-fix`'s own values (§4), and the functional signature multiset matches
`baseline/pre-fix` at 101 of 101.

One further behaviour was intentionally left unchanged, per an explicit prompt instruction: the
generation timestamp (`pipeline_id()`'s return value and the `// Generated at ...` header written
into every file) is not pinned and continues to differ on every run.

## 7. Notes for whoever comes next

- **`validation/check_determinism.sh` is the regression test for I-01 from now on.** Run it after
  any change that could plausibly touch kernel identity, naming, or emission order. It builds
  nothing itself — build first with `validation/build.sh`.
- **The `canonical_string()` fallback branch is defensive, not dead.** It did not fire in this
  verification (§4), but it is not proof it never will — a future prompt (04/05/06) that changes
  what kinds of GiNaC objects reach a kernel's integrand, measure, or Wick product (e.g. by
  activating previously-dead Wick-contraction branches) could introduce a node kind this table
  does not cover. If `grep -l "unhandled GiNaC"` ever matches a run log, treat it exactly like a
  new construct the table needs to be extended for — do not ignore it, and do not assume the
  fallback's plain default-print is safe to leave in place, since that is exactly the
  process-random printing this whole prompt exists to route around.
- **The counterterm map's raw text is not, and is not intended to become, byte-stable.** Gate on
  `validation/canonical_form.py --counterterm-map`, not on `diff`, exactly as prompt 02's log
  already warned.
- **I-10 is a genuinely new, narrower characterisation of the residual GiNaC non-determinism, not
  a regression.** It shows the "per-process hash seed" framing in `RECONCILIATION.md` §3.2 is an
  incomplete description: at *fixed* flags, five independent process launches now agree perfectly,
  which would be surprising if the ordering were purely a fresh random seed per process with no
  further structure. The more precise statement is that a GiNaC object's normalised operand order
  is fixed the first time something forces its hash to be computed and cached, and *that* moment
  depends on the sequence of GiNaC operations the program performs before reaching a given
  expression — which is itself perfectly deterministic for a fixed sequence of flags, but changes
  if the flags change the sequence (as `--counterterms` does, by printing the counterterm map
  before constructing the `LSSEFT` backend). A future investigation of I-10 should start from that
  hypothesis rather than re-deriving it.
- **Dead end avoided:** an early version of the five-run per-file check used a shell loop that
  built an md5 list with plain string concatenation (`sums="$sums $m"`) and compared it with
  `echo $sums | tr ... | sort -u`; this produced a spurious "2 distinct md5s" result for *every*
  file, including ones later shown to be genuinely identical, because of an interaction between
  unquoted word-splitting and the two-line `MD5 (stdin) = <hash>` output format some `md5`
  invocations produce. Switching to `md5 -q` (hash only) and bash arrays fixed it, and
  `check_determinism.sh` uses arrays/explicit comparisons throughout for exactly this reason. If a
  future check of this kind reports a suspicious result, verify the shell plumbing before
  concluding the underlying artefact is unstable.
- **Deliberately not touched:** the dedup key, `LSSEFT_kernel::is_equal`, the container types
  (still `unordered_map`, per the prompt's explicit non-goal), GiNaC's hash seed, and the default
  (non-pinned) generation timestamp.
