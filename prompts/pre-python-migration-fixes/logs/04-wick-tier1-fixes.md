## 1. What this prompt was for

`lib/detail/contractions.{h,cpp}` builds every possible Wick contraction of the initial-value
fields entering a correlation function and decides which momentum symbol to substitute into the
resulting `cfs::Pk(...)` placeholder. Three bugs were dormant there, all confirmed by reading the
code in `RECONCILIATION.md` §2.1 and never independently exercised: a directed graph-connectivity
test that is only accidentally correct for two external legs; two containers (`unassigned`,
`mma_map`) that are keyed by momentum but looked up by field symbol, so six lookups could never
succeed; and four `break` statements that, once those lookups start succeeding, would silently
truncate the Wick product. Fixes (ii) and (iii) mask each other exactly — the prompt's central
warning — so they had to land in the same commit as (i). This is study §7.1 Tier 1 / §9 Phase −1
item 3.

### 4.1 The `[INSTR-KEY]` evidence

Printed once, on the first contraction processed, from the **pre-fix** instrumented build:

```
[INSTR-KEY] left_sym = delta ; left_mom = q0 ; unassigned[left_clust].find(left_sym) found = 0 ;
            unassigned[left_clust].find(left_mom) found = 0 ;
            mma_map[left_clust].find(left_sym) found = 0 ;
            mma_map[left_clust].find(left_mom) found = 1 ;
            unassigned[left_clust] = { } ; mma_map[left_clust] keys = { q0 }
```

This directly demonstrates the bug the study describes: `left_sym` is the literal string `delta`
for every field (every initial value is created via `sf.make_initial_value("delta")`), so
`mma_map[left_clust].find(left_sym)` can never find anything — confirmed here: 0. The same
container, looked up by `left_mom` (`q0`, the momentum this specific field actually carries),
**does** find an entry — confirmed here: 1. This is exactly the failure mode fix (ii) repairs.

It also confirms, independently, the prompt's expectation that the two recovery branches
(`left_unassigned`/`right_unassigned`) remain unexercised even after the fix: `unassigned[left_clust]`
is already empty (`{ }`) by the time `evaluate_Wick_contractions()` runs, in this two-point-function
case, so `find()` fails on `unassigned` regardless of which key is used, `left_unassigned` was
already correctly `false`, and the fix to that lookup's key (symbol → momentum) is inert for
`unassigned` specifically — it only changes behaviour for the `mma_map` lookups (the `t1_simple`/
`t2_simple` branches). See §5 for why this is expected and not a sign the fix is incomplete.

## 5. Behaviour that intentionally changed

**Internally:** the code path taken by 678 of 776 Wick contractions changed, from the unconditional
final fall-through (`Ps.emplace_back(cfs::Pk(l, r, left_mom)...)`) to the new `t1_simple` branch
(`Ps.emplace_back(cfs::Pk(l, r, left_mom)...)` — the *same* expression, reached one branch earlier,
now that `mma_map[left_clust].find(left_mom)` can succeed). This is exactly the study's predicted
678/98 split, reproduced exactly (§4.2).

**Observably, in the emitted `autogenerated/` tree: nothing changed.** This was not assumed; it was
measured (§4, textual diff). The reason, per the prompt's own "why this is expected to be
regression-free" section: `loop_integral::match_Wick_to_Rayleigh()` re-canonicalises every `Pk`
argument against the loop and Rayleigh momenta *after* `evaluate_Wick_contractions()` runs, so
whichever momentum symbol got substituted at contraction time is replaced again downstream by the
same canonical choice regardless of path. The interesting middle of this change, for a future
reader: `t1_simple` at line 534 and `fallthrough` at line 547 emit **textually identical** GiNaC
expressions (`cfs::Pk(l, r, left_mom).subs(mma_map[left_clust])`) — the two branches were always
computing the same thing for every contraction where they overlap, in this two-point-function case;
the difference the fix makes is only that this identical value is now reached one branch earlier and
correctly (with a `continue`) rather than always falling through, which matters only for the
*coefficient count* consequence (`t2_simple`, `left_unassigned`, `right_unassigned`), i.e. for the
break/continue distinction, not for the arithmetic. Nothing about this is guaranteed for N ≥ 3 or a
three-field block — the study is explicit that this is a two-point-function-specific correctness
demonstration, not a proof for the general case.

## 7. Notes for whoever comes next

- **`t2_simple` staying at 0 is expected, not a red flag.** `t1_simple` (checks the *left* momentum
  first) and `t2_simple` (checks the *right* momentum, only reached if the left check fails) are
  mutually exclusive per contraction; in this two-point-function case, whenever `mma_map[left_clust]`
  has an entry for `left_mom`, the algorithm never needs to fall through to check the right side, so
  `t2_simple` never fires. Both `:531` and `:539` (`t1`/`t2`) were fixed identically (§2.1); nothing
  distinguishes them structurally. A three-field block or an N≥3 case could plausibly be the first
  thing that exercises `t2_simple`.
- **The two recovery branches (`left_unassigned`, `right_unassigned`) remain unexercised after this
  fix**, exactly as the prompt warned they would: `unassigned[clust]` is already empty by the time
  `evaluate_Wick_contractions()` runs, for every contraction in every group, in the two-point-function
  case (confirmed directly by the `[INSTR-KEY]` evidence, §4.1, and by both counters staying at 0 in
  both the before and after measurement, §4.2). These branches are the code an *n*-point function or
  a three-field block will exercise for the first time, and they remain untested by this campaign.
  A future prompt that reaches N ≥ 3 should not assume they are correct merely because they compile
  and match the two Tier-1 fixes' *shape* — they were written but never run.
- **`assign_external_momenta`'s stale comment and its `labels.size() > 2` skip were left alone, as
  instructed** (explicitly out of scope for this prompt — Tier 2, belongs with the spanning-tree
  work). Recorded here per the prompt's explicit request: the comment at `contractions.h:373-375`
  says "if there is *more than one* unassigned momentum left in this cluster, then do nothing", but
  the code tests `labels.size() > 2`, i.e. it only takes the "do nothing" branch when there are
  *three or more* unassigned momenta, not "more than one" (two would fall through to the
  single-assignment logic below, which then only reads `*labels.begin()` and silently ignores the
  second label — a latent bug of its own, not touched here). The study measured the unassigned set
  at this point as always of size exactly 1 across 780 calls in a full run, so in this repository at
  this commit neither the `> 2` skip nor a genuine size-2 case has ever actually run; this was not
  independently re-measured in this prompt (out of scope), but nothing in the Wick Tier-1 fixes
  changes what reaches `assign_external_momenta`, so there is no reason to expect the study's count
  to have changed.
- **Dead end avoided:** none — this prompt's fixes applied cleanly on the first attempt, with every
  measured number matching the study's prediction exactly (branch counts, functional signatures,
  `compute_*` names, warnings, counterterm map, dedup, and — unexpectedly strongly — full textual
  identity of the emitted tree). No investigation of a discrepancy was needed.
- **For prompt 05/06:** neither touches `lib/detail/contractions.{h,cpp}`, so this file's
  instrumentation-removal state (§3.2 D-1) should still be current when they run. If a later prompt
  in this campaign (or the port) needs to re-instrument `evaluate_Wick_contractions()` for an N≥3 or
  three-field case, the counters and the `[INSTR-KEY]` print used here (§4.1, §4.3) are a ready-made
  starting point.
