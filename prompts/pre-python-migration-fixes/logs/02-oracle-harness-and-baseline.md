## 1. What this prompt was for

`LSSEFT-analytic` has no tests of any kind, and `diff` cannot serve as one: two runs of the same
binary with identical flags emit different `autogenerated/` trees. This prompt built the
*functional* differential harness that every later prompt — and every stage of the planned Python
port — will use as its regression test, measured and wrote up exactly how the non-determinism
behaves, and archived the pre-fix output as a tagged baseline. It changes no program source
whatsoever: everything new is under `validation/`, plus campaign bookkeeping.

## 3. Divergences from the prompt

### 3.1 Structurally required

> **D-1 — "the counterterm map, canonicalised (sorted lines) so it is comparable despite I-01"
> does not, in fact, make it comparable**
> **Prompt asked:** work item 4 — archive "the counterterm map, canonicalised (sorted lines) so it
> is comparable despite I-01".
> **Shipped:** the prescribed artefact, under the name `counterterm-map.sorted-lines.txt` and with
> a header that tells the reader not to compare with it; **plus** `counterterm-map.canonical.txt`,
> produced by a new `canonical_form.py --counterterm-map` mode which recursively sorts the operands
> of every commutative `*` and every `+`/`-` term list and normalises leading signs.
> **Obstacle:** measured. The sorted-lines form gives **four distinct md5s across the five runs**
> (`d823cbc0…`, `fa8869a8…`, `6101b518…`, `fa8869a8…`, `e4106073…`), so it is not comparable — it
> fails at the one job the prompt gives it. The reason is that the variability is *inside* each
> line, not in the order of the lines: the label multiset is identical in all five runs (md5
> `37e9884e73a65cfa92ad75a19831ca35`), the line count is 760 every run, and 478 entries are `= 0`
> every run. What moves is GiNaC's own operand order within a default-printed expression:
> ```
> run1:  -> mu^0 = -1/30*(56*DE(z)-26*DJ(z)+ … )*Pi^(-2)*D(z)*Pk(delta,delta,k)*…
> run2:  -> mu^0 = -1/30*Pi^(-2)*(56*DE(z)-26*DJ(z)+ … )*D(z)*Pk(delta,delta,k)*…
> ```
> Sorting lines cannot reach that, because no container of *ours* is involved.
> **Why this is minimal:** the prescribed file is still shipped, byte-for-byte the prescribed
> content, because it is the raw artefact prompt 03 has to make byte-stable and the baseline must
> contain it. The addition is the smallest thing that satisfies the prompt's actual stated purpose
> ("so it is comparable"): a purely textual print-order canonicalisation — no algebra, no
> re-parsing into SymPy, no canonicalising printer inside GiNaC, and no source change. It was
> **verified sufficient**: one md5, `1c177140d3688e558b445609f8c585a4`, across all five runs *and*
> the `--auto-symmetrize` run — six independent processes. It deliberately does no algebra (it will
> not see through distribution, `2*a` vs `a+a`, a factor moved across a bracket, or a change of
> exponent form), so a real change to the map still shows up.
>
> Two intermediate attempts are worth recording, because they show how narrow the residue is.
> Sorting only *top-level* multiplicative factors reduced the five runs from four md5 classes to
> two; the remaining split was entirely a leading unary minus binding to a different factor
> (`-Pi^(-2)*D(z)^4*…` vs `-D(z)^4*L0^2*Pi^(-2)*…`). Normalising the sign as well, and recursing
> into nested sums, collapsed it to one. So the whole of the counterterm map's run-to-run variation
> is commutative reordering — which is a materially stronger statement for I-01 than "the label
> multiset is stable", and it means a regression test on the map can be built **today** rather than
> waiting for prompt 03.
>
> Naming note: `canonical` was given to the file that is actually canonical, and the prescribed
> sorted-lines artefact renamed to say what it is. A reader looking for "the canonicalised
> counterterm map" should get the one that works.

> **D-2 — the prompt's literal emitted-code shape does not match the emitter**
> **Prompt asked:** work item 1 gives the shapes to match as
> `double value_ = <expr>;` / `double Wick_  = <expr>;` (two spaces before the `=` on the Wick
> line).
> **Shipped:** `^\s*double\s+value_\s*=\s*(?P<expr>.*);\s*$` and the `Wick_` analogue — whitespace
> tolerant.
> **Obstacle:** `backends/LSSEFT.cpp:726` emits `"   double Wick_ = "` with a *single* space

### 3.2 Implementation choices

> **D-3 — `canonical_form.py` is the shared parsing layer; `compare_autogenerated.py` imports it**
> **Prompt asked:** two scripts, each described independently. Both need the same regexes and the
> same exact-rational parse.
> **Shipped:** `canonical_form.py` owns extraction, the C++→Python rewrites and `parse_exact`;
> `compare_autogenerated.py` does `sys.path.insert(0, <this file's dir>)` and imports it.
> **Options considered:** (a) duplicate the ~60 lines of parsing in both scripts; (b) a third
> shared module, e.g. `validation/_emitted.py`; (c) the import shipped.
> **Criterion used:** (a) guarantees the two will drift apart, and a comparison gate that parses
> differently from the diagnostic beside it is a trap. (b) adds a file the prompt's deliverable
> list does not name, for no benefit over (c). The prompt describes `canonical_form.py` as the
> thing that "re-parses an emitted `value_` expression into SymPy with exact rationals", which is
> precisely the shared layer, so (c) puts the code where the prompt already says it lives.
> **Trade-off a later reader might weigh differently:** the dependency direction is now
> comparator → diagnostic, which reads slightly backwards (the gate depending on the
> non-gate). A reader who dislikes that should move the parsing into a third module rather than
> duplicate it.

> **D-4 — exact-rational evaluation points and mpmath, rather than float points**
> **Prompt asked:** "a fixed set of pseudo-random `(k, q, z)` points — a seeded RNG"; "compare
> exactly where you can. Where you must compare floats, use a relative tolerance and *state it in
> the report*."
> **Shipped:** the points are exact `Rational(n, 1000003)` values drawn with
> `random.Random(20260904).randrange(...)`; each kernel is lambdified to mpmath and evaluated at
> `mp.dps = 60`; the signature key is the value rounded to 25 significant digits; a fallback
> pairing pass at relative tolerance `1e-20` is applied only to signatures the exact key failed to
> pair, and the run's output always prints the seed, the point count, the precision, the tolerance
> and the surrogate `P(k)`.
> **Options considered:** (a) fully exact symbolic evaluation (`.evalf` on exact-rational
> substitutions, or exact algebraic arithmetic) — but the Wick products contain
> `sqrt(k²+q²−2kqz)`, so "exact" means algebraic numbers and a large slowdown for no gain;
> (b) IEEE doubles with `math.isclose` — cheap, but only ~15 digits of headroom, which is thin
> when a real change might be a small rational coefficient shift; (c) the shipped hybrid.
> **Criterion used:** the *inputs* must be exact (that is where the study lost time — float
> literals produce 1e-16 residuals that look like disagreements), the *outputs* only need enough
> precision that a real change cannot hide. 60 digits with a 25-digit key gives 35 digits of
> margin.
> **Trade-off a later reader might weigh differently:** 25 digits is arbitrary. It was chosen
> because, in practice, two trees emitting the same expression modulo GiNaC term order parse to
> *structurally identical* SymPy objects and therefore evaluate bit-for-bit identically — measured:
> all 101 pairs in the 2018 comparison matched on the exact key, with the tolerance fallback never
> firing. Someone could argue for keying on fewer digits and leaning on the tolerance pass instead.

> **D-5 — `randrange` integer draws, not `random.random()`**
> **Prompt asked:** a seeded RNG, "the seed recorded in the output, so the comparison is
> repeatable."
> **Shipped:** integer draws from `random.Random(seed).randrange(lo, hi)`, turned into exact
> rationals over a fixed prime denominator.
> **Options considered:** `random.random()` floats; `numpy.random` with a fixed bit generator;
> the shipped integer draws.
> **Criterion used:** "repeatable" has to mean repeatable in two years on a different Python.
> Mersenne-Twister *integer* draws are the most stable part of that API; `random.random()`'s
> float construction and `numpy`'s legacy/Generator split are both things that have moved before.
> A prime denominator (`1000003`) was chosen so the sampled coordinates share no factor with the
> small integer coefficients in the emitted kernels and cannot accidentally cancel a term.
> **Trade-off a later reader might weigh differently:** this ties reproducibility to CPython's
> `random` module rather than to a self-contained PRNG written out in the file. A hand-rolled LCG
> would be fully self-describing at the cost of being less obviously unbiased.

> **D-6 — the signature keeps `value_` and `Wick_` as separate components**
> **Prompt asked:** "the multiset of (integrand × Wick product) signature vectors".
> **Shipped:** a 50-component vector — 25 `value_` evaluations followed by 25 `Wick_` evaluations
> — rather than 25 evaluations of their product.
> **Options considered:** the product (literally what the phrase says, and what
> `kernel_integrands.cpp` actually integrates: `f_[0] = jacobian * value_ * Wick_`); the
> concatenation shipped.
> **Criterion used:** strictly more discriminating at no cost. Two kernels whose product agrees
> but whose factorisation differs — e.g. a factor migrating between the integrand and the Wick
> product — are genuinely different emitted artefacts, and a regression that moved one would be
> invisible to the product form.
> **Trade-off a later reader might weigh differently:** it makes the harness sensitive to a
> refactor that is *physically* harmless but moves a factor across the value/Wick boundary. If a
> later prompt legitimately does that, this will fail and the log will have to say so — which is
> the correct outcome, but it is a cost.

> **D-7 — the surrogate `P(k)`, the sampling ranges, and the degeneracy guard**
> **Prompt asked:** "a surrogate power spectrum", unspecified.
> **Shipped:** `P(x) = x / (7x⁴ + 3x² + 1)` — positive on `x > 0`, decaying like `x⁻³`, a rational
> function so it introduces no irrational constant of its own. Points are drawn with
> `k_ ∈ [0.05, 1)`, `q_ ∈ [0.05, 5)` (straddling `k_`, so both `q_ < k_` and `q_ > k_` occur) and
> `z_ ∈ [-0.9, 0.9)`; a point is rejected and redrawn if `q² + k² − 2qkz < 10⁻⁶`.
> **Options considered:** a realistic ΛCDM `P(k)` (an actual transfer function or a fitting
> formula); a bare power law `x^n`; the shipped rational function.
> **Criterion used:** the surrogate only has to be identical on both sides and non-degenerate.
> A realistic `P(k)` would add a dependency and a source of numerical noise for zero benefit;
> a bare power law risks accidental algebraic coincidences between kernels. The `z_` range stops
> short of ±1 because `q² + k² − 2qkz` is the denominator of nearly every kernel and the argument
> of the sqrt in nearly every Wick product — the emitted code has `z_ = 2*x_[1] − 1 ∈ [−1, 1]`,
> and the endpoints are exactly where that vanishes for `q ≈ k`.
> **Trade-off a later reader might weigh differently:** staying off the endpoints means the
> harness never probes the IR/collinear corner, which is where the study's `is_IR_safe` concerns
> (I-06) live. That is deliberate — this is an equality test, not an asymptotics test — but a
> reader wanting IR coverage would need a second, separately-toleranced point set.

> **D-8 — `--emit-signatures` / `--signatures`, and `__pycache__/` in `.gitignore`**
> **Prompt asked:** work item 4 requires "the signature multiset computed by
> `compare_autogenerated.py`, serialised, together with the RNG seed used, so later prompts can
> compare against the *stored signatures* without re-running the pre-fix code." No interface was
> specified.
> **Shipped:** two flags on the comparator rather than a separate serialiser script.
> `--emit-signatures FILE` writes the multiset with the seed, the 25 points, the ranges, the
> precision and the surrogate; `--signatures FILE` compares a tree against such a file and
> **refuses** if the stored seed / point count / denominator / key width differ from the script's
> current constants, rather than silently producing a meaningless answer.
> Adding Python under `validation/` also meant `__pycache__/` had to be gitignored; that line was
> not asked for.
> **Options considered:** a third script; a `--dump` mode; the two flags shipped.
> **Criterion used:** the deliverable list names three scripts and this is not one of them, so the
> functionality belongs on the script that already computes the thing.
> **Trade-off a later reader might weigh differently:** the comparator's argument surface is now
> slightly overloaded (`left` alone + `--emit-signatures` behaves differently from `left right`).

> **D-9 — the GiNaC probe also prints the expression hash**
> **Prompt asked:** work item 3 gives the probe's source verbatim; it prints only the expression.
> **Shipped:** the same program, plus `<< " hash of Pi^(-2) = " << GiNaC::pow(GiNaC::Pi,-2).gethash()`.
> **Options considered:** the prompt's listing unmodified; the one-expression addition shipped.
> **Criterion used:** `RECONCILIATION.md` §3.2 presents its evidence *as* expression-plus-hash, and
> the hash is the actual carrier of the non-determinism — with only the printed expression, a run
> that happens to produce the same ordering twice looks like evidence *against* the finding. With
> the hash, five runs give five different hashes even where two orderings coincide, which is the
> unambiguous signal.
> **Trade-off a later reader might weigh differently:** it makes the probe's output one column
> wider than the text in `RECONCILIATION.md` and the prompt, so a byte-comparison against those
> documents will not match.

> **D-10 — the baseline is run 1 of the five-run study, not a separate sixth run**
> **Prompt asked:** work items 3 and 4 as separate activities.
> **Shipped:** `validation/baselines/pre-fix/` is a copy of `validation/out/run1`.
> **Options considered:** a dedicated sixth run; reusing run 1.
> **Criterion used:** a sixth run would be a sixth arbitrary draw from the same distribution and
> would tell us nothing extra, while costing 45 s and breaking the ability to say exactly where in
> the non-determinism table the archived tree sits. `manifest.json` records the identification.
> **Trade-off a later reader might weigh differently:** it means the baseline's `kerNNN` numbering
> is one particular random draw. That is unavoidable pre-prompt-03 and is exactly why the gate is
> a multiset.

> **D-11 — `run.log` archived verbatim, with ANSI colour codes**
> **Prompt asked:** "the captured stdout/stderr of that run".
> **Shipped:** the file as captured, escape sequences intact; the ANSI-stripped projections live in
> `warnings.txt` and the two counterterm-map files, each carrying its regeneration pipeline in a
> header comment.
> **Options considered:** strip the escapes in place (nicer to read and to diff); keep verbatim.
> **Criterion used:** "captured stdout/stderr" is an evidentiary artefact; a filtered copy is a
> derived one. Both are present, with the derivation written down.
> **Trade-off a later reader might weigh differently:** `git diff` on `run.log` is unpleasant.

### 4.2 The negative test

Two independent perturbations of a **scratch copy** of run 1 (under the session scratchpad, never

in `ker99`:

| Perturbation | Result |
|---|---|
| `*1575.0` → `*1576.0` (a 6×10⁻⁴ relative change) | `signatures matched: 100 of 101`; `MISMATCH: 1 signature(s) only in A, 1 only in B`; both reported as `ker99`; exit 1 |

## 7. Notes for whoever comes next

- **Run `compare_autogenerated.py`, not `diff`.** Ten of 22 files differ between two identical
  runs. If you diff the tree you will see hundreds of lines of noise and stop trusting the test.
  This is the single most likely way to waste an afternoon in this repository.
- **The evaluation-point constants are load-bearing.** They are in one marked block at the top of
  `compare_autogenerated.py`. Touching any of them invalidates `signatures.json`. The script will
  tell you so rather than lie to you, but re-baselining means the pre-fix reference is no longer
  directly comparable to anything captured before your change.
- **`canonical_form.py` fails loudly on unknown identifiers, and that is deliberate.** If prompt 04
  or 05 causes the emitter to produce a construct the rewrites do not cover, you will get
  `ValueError: unrecognised identifier(s) …` rather than a silently wrong comparison. Teach
  `_REWRITES` / `_KNOWN_TOKENS` and say so in your log.
- **The harness is sensitive well below double precision** (§4.2: it catches a 6×10⁻¹⁶ relative
  coefficient change). Do not assume a "rounding-level" difference will slip through; if the gate
  fires, something really did change.
- **Prompt 03 should not promise byte-equality of the counterterm map.** §3.1 D-1 and
  `NONDETERMINISM.md` §3.2/§4 show why: the residue is GiNaC's default-print operand order, which
  is not reachable by sorting our own containers. The `csrc`-printed integrands, by contrast, are
  already stable 5/5, so a byte-reproducible `autogenerated/` tree (modulo the two timestamp sites)
  does look attainable. Measure, do not assume. What prompt 03 *can* rely on is that the map's
  content is already verifiably stable — `canonical_form.py --counterterm-map` gives one md5 across
  six processes — so it has a working regression test for the map from day one and does not need to
  solve byte-stability before it can validate anything.
- **`csrc`-printed integrand text is stable across *processes* but not across *construction
  paths*.** §5a: the `--auto-symmetrize` run differs from the canonical run in 80 of 101 `value_`
  lines while being functionally identical. If prompt 04 or 05 changes how expressions are built,
  expect the emitted text to move even where the physics does not — and trust the signature
  multiset, not the md5.
- **Always exclude `// Generated at …` and `pipeline_id.cpp`** from any byte comparison — both are
  timestamps (`backends/LSSEFT.cpp:619, 1534`).
- **Dead end avoided:** the first attempt at the negative test tried to perturb "the first `*3.0`
  coefficient" in the first `value_` line and silently found no such literal, so the "perturbed"
  copy was byte-identical to the original and the harness dutifully reported MATCH. That is a good
  reminder that a negative test needs its *perturbation* verified, not just its outcome: the
  shipped procedure asserts that the substitution actually fired and prints the before/after line.
- **Deliberately not touched:** the six duplicate kernels (I-05), `is_IR_safe` (I-06), the
  `unordered_map`s themselves (prompt 03), and `~/Documents/Code/LSSEFT/autogenerated/`, which was
  only ever read.
