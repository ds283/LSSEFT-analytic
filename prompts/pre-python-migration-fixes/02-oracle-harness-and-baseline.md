## Why the comparison must be functional, not textual

`diff` on the generated tree is **not** a usable regression test, for reasons measured during
planning and written up in `RECONCILIATION.md` §3:

- GiNaC 1.8.10 seeds its expression hash from a runtime address, so operand ordering inside printed
  expressions varies **between processes**.
- `one_loop_element_key::hash()` and `LSSEFT_kernel::hash()` hash *default-printed strings*; those
  hashes key two `std::unordered_map`s; those maps drive kernel naming and file emission order.
- Consequence: two runs of the same binary with identical flags produced **four different**
  `kernel_integrands.cpp` files across four runs, while the sorted set of `value_` strings was
  byte-identical every time.

Prompt 03 will fix as much of that as is fixable. This prompt must work *without* assuming it is
fixed, because it has to capture the pre-fix state.

## Work item 1 — the functional comparison (study Appendix B.1)

Write `validation/compare_autogenerated.py`. It takes two `autogenerated/` directories and answers:
*do these two trees define the same set of integrands, as functions?*

Method, from the study:

1. Regex the `value_` and `Wick_` expressions out of `kernel_integrands.cpp`. The shapes to match
   are, per kernel:
   ```cpp
   static int kerNNN_integrand(const int* ndim_, const cubareal x_[], ...)
   ...
      double value_ = <expr>;
      double Wick_  = <expr>;
   ```
2. Map the emitted C++ to Python: `std::pow` → `pow`, drop the `Mpc_units::*` unit factors, map the
   `data_->Pk((<expr>)/Mpc_units::Mpc) / Mpc_units::Mpc3` calls onto a surrogate power spectrum.
   The free variables are `k_`, `q_`, `z_` (see `backends/LSSEFT.cpp:698-712` for how they are
   introduced).
3. Evaluate each (value, Wick) pair at a **fixed** set of pseudo-random `(k, q, z)` points — a
   seeded RNG, and the seed recorded in the output, so the comparison is repeatable. 25 points was
   enough during the study; use at least that.
4. Compare the **multisets** of signature vectors, not the per-kernel mapping. This is insensitive
   to kernel renumbering and to GiNaC term ordering, which is exactly what is needed.
5. Report: number of kernels on each side; number of signatures matched; any signature present on
   one side only, with the `kerNNN` labels that carry it.

Two things the study flags from experience, both of which cost it time:

- **Parse with exact rational literals.** Use SymPy's `rationalize` transformation so that
  `-(2.0/5.0)` becomes `Rational(-2,5)`. Parsing with default float literals produces 10⁻¹⁶
  residuals that look like real disagreements and are not.
- Tolerance: compare exactly where you can. Where you must compare floats, use a relative tolerance
  and *state it in the report*.

The script must exit non-zero on mismatch and print something a human can act on.

## Work item 2 — the canonical-form utility (study Appendix B.2)

Write `validation/canonical_form.py`, providing:

- re-parse of an emitted `value_` expression into SymPy with exact rationals;
- `cancel(together(·))` reduction;
- a `--dedup` mode that reports how many of the emitted kernels are algebraically distinct.

This is a diagnostic, not a gate. It was run during planning and reproduces the study's §3.4
result exactly: **101 emitted, 95 distinct, 6 duplicate pairs**, keyed jointly on the `Wick_`
string. Confirm you get the same numbers; record them. Do **not** act on the duplicates — changing
the dedup key is out of scope (issue I-05).

## Work item 3 — characterise the non-determinism

Run the canonical configuration **five times** into five separate output directories and record:

| Quantity | How to compute |
|---|---|
| md5 of each `autogenerated/*.cpp` | per file, per run |
| md5 of the sorted set of `double value_` lines | `grep "double value_" … \| sed 's/^ *//' \| sort \| md5` |
| md5 of the sorted set of `double Wick_` lines | as above |
| set of `compute_*` names | `grep -o 'compute_[A-Za-z0-9_]*' … \| sort -u` |
| counterterm map, sorted lines | from the run log, after `** COUNTERTERM MAP` |
| warning set | grep the run log |

Expected from planning (four runs), so you have something to check against:

- the sorted `value_` set and the sorted `Wick_` set were byte-identical across all runs;
- the `compute_*` name set was identical across runs *and* identical to the 2018 reference;
- `kernel_integrands.cpp` as a whole gave four distinct md5s;
- the sorted counterterm map gave three distinct md5s across four runs;
- 10 of 22 generated files differed between two consecutive identical runs.

Write the results into `validation/NONDETERMINISM.md`, together with the causal chain from
`RECONCILIATION.md` §3.2 (cite the file:line anchors; do not re-derive them). This document is the
input to prompt 03 and the evidence for issue I-01, so make it precise about **which artefacts are
stable and which are not**.

Also record the minimal GiNaC reproduction, so a future reader does not blame this project for a
library behaviour:

```cpp

  GiNaC::symbol a("a"), b("b"), z("z");
```

Run it five times. During planning this printed three different orderings in five runs. Keep the
source under `validation/` so the check can be repeated after a GiNaC upgrade.
