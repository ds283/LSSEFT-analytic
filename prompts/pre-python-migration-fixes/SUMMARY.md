# Campaign summary — pre-Python-migration fixes to `LSSEFT-analytic`

**Campaign:** `prompts/pre-python-migration-fixes/`
**Span:** 2026-09-04 (prompts 01-06) to 2026-09-05 (two out-of-band commits, then prompt 07)
**Written by:** prompt 07, at close-out

This document is a factual account of what the campaign actually did, for someone deciding whether
to trust `LSSEFT-analytic` as a differential oracle for the planned Python/SymPy port. It is not a
re-statement of the prompts (`prompts/pre-python-migration-fixes/0N-*.md`) — read those, and the six
logs in `logs/`, for the reasoning behind each decision. This document collects the facts that would
otherwise require reading all seven prompts and seven logs to assemble.

The one document a port author needs on day one is `validation/ORACLE.md`, not this one. This
document is the campaign's own record.

---

## 1. Why the campaign existed

The feasibility study for the Python port
(`~/Documents/Code/ScaleDependentBias/documents/python-migration/LSSEFT-analytic-feasibility.md`)
concluded that the port is feasible because the C++ program can be rebuilt and run as a differential
oracle at every step of the port — provided the oracle's own known defects are fixed first, so that a
port author cannot mistake an oracle bug for a port bug. This campaign implements the study's
"Phase −1" (repair the oracle) and "Phase 0" (archive tagged pre-fix/post-fix baselines). Full
background: `prompts/pre-python-migration-fixes/README.md`.

**Success criterion, stated at the outset and confirmed at the end:** the same 101 kernels and 135
`compute_*` assembly functions, produced reproducibly, from a build needing only a C++17 compiler and
`pkg-config ginac`, with the latent defects removed and the remaining uncertainties written down. See
§5 of this document for the final comparison numbers that establish this.

## 4. What changed behaviourally

The honest answer, after all seven prompts: **kernel naming order; the evaluation of `FabJ` by
closed form instead of a lookup table, which changes printed form but not values; and one new
run-time assertion that a zero-valued Rayleigh label never survives to the reduction stage — nothing
else.**

1. **Kernel naming order** (prompt 03). Before: `ker0..ker100` were assigned in `unordered_map`
   bucket order, itself a function of GiNaC's per-process expression-hash seed, so the same physical
   kernel could be `ker38` in one run and `ker71` in the next. After: names are assigned once, from a
   full sort on a print-order-independent canonical key, so a kernel's content determines its name
   and position deterministically. No integrand's *value* changed.

2. **`FabJ` evaluated by closed form, not table** (the 2026-09-05 follow-up, `5e2b208`). Before:
   `lib/detail/special_functions.cpp` looked up `FabJ(0, n, n)` in a hand-written table valid only for
   `n ≤ 4`, throwing `WARNING_UNEVALUATED_FABRIKANT` outside that range (never observed to fire on
   the current operator basis). After: the closed form
   `FabJ(0,n,n;s,t,u) = π/(4stu) · Pₙ((t²+u²−s²)/(2tu))`, valid for every `n`, because the reduction's
   own integration order (Rayleigh direction first) guarantees only the `σ=0` family is ever produced
   (`~/Documents/Code/ScaleDependentBias/documents/LEGACY-CODE-AUDIT.md` §1.3, §4.2, corrected).
   This changes the *printed* term arrangement of 47
   of the 101 emitted `value_` expressions (confirmed count, §3) and, as a direct consequence, the
   kernel-numbering permutation on top of prompt 03's — but it changes no kernel's *value*: 101 of 101
   signatures still match `baseline/pre-fix` functionally, and the Wick-product half of every kernel
   is textually untouched.

3. **A new assertion, `ERROR_RAYLEIGH_ZERO_LABEL_SURVIVES`** (the 2026-09-05 follow-up, `69cae4a`).
   Added in the `one_loop_reduced_integral` constructor, immediately after
   `K = dot_products_to_cos(K).expand()`: for every Rayleigh rule whose value collapsed to zero, its
   label must not still appear in `K` or in the Wick product. This never fires on the current
   operator basis (verified: emitted tree byte-identical with and without it) and is a genuine
   safety net, not a behavioural change to any published number — but it is new run-time code that
   did not exist before the campaign, so it is listed here for completeness.

**Nothing else changed.** In particular: no dedup key, no `is_IR_safe` logic, no bias-filter
registration, no numerical value of any of the 101 kernels or the counterterm map, changed at any
point in the campaign. Every prompt's log demonstrates this with an explicit before/after comparison,
not merely asserts it.

## 6. Every implementation-choice divergence, collected in one place

Each of the six prompt logs classifies every point where the shipped code differs from the prompt's
literal instruction as **structurally required**, an **implementation choice**, or **unintended
drift** (`README.md`'s logging discipline). This table collects every entry the logs classified as an
**implementation choice** — i.e. a point where more than one workable option existed and a judgement
call was made — so a reviewer can see every judgement call made in the campaign without reading six
logs. (Entries classified as *structurally required* or *unintended drift* are not duplicated here;
see the individual logs — `logs/0N-*.md` §3.1/§3.3 — for those.)

| Log | ID | What was decided |
|---|---|---|
| 01 | D-1 | Hand-rolled `argv` parser as a flat `if`/`continue` chain (not a dispatch table), matching `services/switches.h`'s own layout. Two narrowings vs. `boost::program_options`, both explicitly authorized by the prompt: no long-option prefix abbreviation, no `-opath` attached-value form. |
| 01 | D-2 | `cmake/CompilerFlags.cmake`'s warning suppressions, which only apply under `CMAKE_BUILD_TYPE=Release`/`Debug`, left as-is rather than made unconditional — `validation/build.sh` always passes an explicit build type, so the gap never bites this campaign's own tooling. |
| 02 | D-3 | `canonical_form.py` owns extraction/parsing; `compare_autogenerated.py` imports it, rather than duplicating the ~60 lines of regex/parse logic or introducing a third shared module. |
| 02 | D-4 | Evaluation points are exact rationals (prime denominator `1000003`), evaluated in mpmath at 60 digits with a 25-significant-digit signature key and a `1e-20` tolerance fallback that is never exercised in practice — chosen over both fully-exact algebraic evaluation (too slow, given `sqrt` terms) and plain IEEE doubles (only ~15 digits of headroom). |
| 02 | D-5 | `random.Random(seed).randrange(...)` integer draws, not `random.random()` floats or `numpy`'s RNG — chosen for the most stable long-term reproducibility guarantee across Python versions. |
| 02 | D-6 | The signature vector keeps `value_` and `Wick_` as 25+25 separate components, not their 25-point product — strictly more discriminating (catches a factor migrating between the two) at no extra cost. |
| 02 | D-7 | Surrogate `P(k) = k/(7k⁴+3k²+1)` (positive, ~`k⁻³`, rational, introduces no irrational constant of its own), with `k_∈[0.05,1)`, `q_∈[0.05,5)`, `z_∈[-0.9,0.9)` and a degeneracy guard — deliberately does not probe the IR/collinear corner (that is an asymptotics question, not an equality test). |
| 02 | D-8 | `--emit-signatures`/`--signatures` added as flags on the comparator rather than as a third script, since the prompt's deliverable list names only three scripts and this functionality belongs on the one that already computes the signatures. |
| 02 | D-9 | The GiNaC ordering probe (`validation/ginac_ordering_probe.cpp`) prints the expression hash alongside the printed form, beyond the prompt's own verbatim listing — the hash is the unambiguous signal that two runs producing the same *printed* ordering by chance are still hashing differently. |
| 02 | D-10 | `baseline/pre-fix` is archived from run 1 of the five-run non-determinism study, not a separate sixth run — a sixth run would be an arbitrary draw telling us nothing extra, at the cost of losing the archived tree's place in that study's table. |
| 02 | D-11 | `run.log` is archived verbatim, ANSI escape codes intact, with separate ANSI-stripped derived files (`warnings.txt`, the two counterterm-map projections) for anything meant to be read or diffed. |
| 03 | D-1 | `canonical_string()`'s fallback branch (default-GiNaC-print plus a one-time stderr warning for any node kind outside the seven-rule table) never fired in a full run — reported as a measured fact, not assumed safe. |
| 03 | D-2 | The 15 emission-loop edits add one rebinding line (`const auto& record = record_ref.get();`) rather than rewriting every `record.first`/`.second` reference in each loop body, keeping each of the 15 diffs a small, obviously-correct two-line change. |
| 03 | D-3 | Kernel naming deferred to a new `finalize_kernel_names()`, called once from `write()`, which therefore changes from `const` to non-`const` — chosen over marking four members `mutable` (which would permit mutation from *any* `const` method) or inventing an unenforceable "last `add()` call" contract. |
| 03 | D-4 | `canonicalize_Rayleigh_labels()` left untouched: unlike a kernel's name, the `R0`/`R1`/... label is substituted directly into the kernel's algebraic content, so reordering its traversal risks a content change dressed as a determinism fix. Empirically unnecessary anyway — the relevant output was already byte-stable before this prompt touched anything. |
| 03 | D-5 | The counterterm map's *line* order was found already deterministic pre-prompt-03 (investigated and explained); its *intra-line* GiNaC print order was left to the existing canonicalising comparison (`canonical_form.py --counterterm-map`, built in prompt 02) rather than building a canonicalising printer — the cheaper, already-verified-sufficient option, given the map is a human-readable diagnostic, not a parsed artefact. |
| 04 | D-1 | Temporary instrumentation (branch counters, the `[INSTR-KEY]` diagnostic) removed entirely before commit, not gated behind a compile-time flag — no known future consumer in prompts 05/06's scope justified carrying dead instrumentation code. |
| 05 | D-1 | The shared factor-enumeration helper is two layers: `utilities/GiNaC_utils::to_exvector` (extended, not reimplemented, to handle non-`mul` arguments) plus a new `one_loop_reduced_integral::extract_Legendre_factors` layering the Legendre-specific logic on top — chosen over a single-layer helper wholly inside `one_loop_reduced_integral.cpp`, since `to_exvector`'s bug (assuming a `mul` argument) is a defect in its own right, worth fixing at its actual site. |
| 05 | D-2 | `validation/test_neumann_adams.cpp` is a standalone re-expression of the closed form, not a test linked against the production `A()` — linking against `one_loop_reduced_integral.cpp.o` directly was attempted and abandoned: object files pull in the whole translation unit's dependency graph, which would have meant adding a permanent CMake test target for one pure function. |
| 05 | D-3 | The one-Rayleigh site's new shape guard reuses the existing `ERROR_BADLY_FORMED_LEGENDRE_SUM_TERM` constant rather than minting a new one — both sites now guard against exactly the same condition with accurate, non-misleading text. |
| 06 | D-2 | The invariant was tested inside `Pk_one_loop::cross_product`, at the same pipeline stage `prune_Rayleigh_list` itself already uses for a structurally identical membership test — chosen because the prompt's own hint pointed there, and because `merge_Rayleigh_rules` (where the rule's value is actually computed) has no access to `K` at all. |
| 06 | D-3 | The invariant test was sharpened from "does the label occur anywhere in `K`" to "does it occur in `K`'s normalised denominator" — run alongside the literal test at no extra cost, and shown to give an identical result for a documented reason (GiNaC's `.normal()` treats every `indexed` object as an opaque atom, so it cannot see the `(L.i)²(L.j)⁻²=1` cancellation either). |

Two further points, not phrased as `D-N` items in their logs but worth surfacing here because they
bear directly on how much to trust the oracle:

- **Log 04's headline finding** — that the Wick Tier-1 fix activates 678 previously-dead branches yet
  changes not one byte of emitted output — is not a coincidence to be generalised. It holds because
  `loop_integral::match_Wick_to_Rayleigh()` re-canonicalises the printed `Pk` argument after
  contraction, on the *current two-point-function basis*. Log 04 §7 is explicit that this masking is
  not guaranteed for an *n*-point function or a three-field block, which is precisely the case the
  campaign's Tier-2/Tier-3 deferrals (§5 above) would exercise.
- **Log 06's reversal** (§3.1 of `logs/06-rayleigh-zero-diagnosis.md`, its addendum, and
  `validation/RAYLEIGH-ZERO-FINDINGS.md` §8) is not an "implementation choice" in the same sense as
  the table above — it is a corrected measurement, not a judgement call — but it is the single most
  consequential thing that happened in this campaign outside the numbered prompts, and it is why
  `validation/ORACLE.md` devotes a dedicated section to Rayleigh momenta rather than a passing
  mention.
