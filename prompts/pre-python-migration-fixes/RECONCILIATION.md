**Source document:** `~/Documents/Code/ScaleDependentBias/documents/python-migration/LSSEFT-analytic-feasibility.md`

This document records what was checked, what was confirmed, what was corrected, and what was
*newly discovered* while preparing the implementation campaign. Its purpose is to spare every
later agent the cost of re-deriving these facts. Where the campaign prompts assert something,
the evidence is here.

and running the code on this machine (Apple clang 21.0.0, arm64, GiNaC 1.8.10 from MacPorts,
CMake 3.31.11, Python 3.14.4 / SymPy 1.14.0 / mpmath 1.4.0). Everything marked **[read]** was
verified by reading source. Everything marked **[unverified]** is repeated from the study and has
*not* been independently checked here.

### 2.2 `A(r)`: reproduced numerically

Transcribing the exact `unsigned int` arithmetic of `one_loop_reduced_integral.cpp:738-763`:

```
A(10) = 654729075/3628800   = 180.425781250   (correct)
A(11) = 864408687/39916800  =  21.655260116   (correct value 344.4492...)
A(12) = 2701530617/479001600 =  5.639919819
```

This matches the study's table digit for digit. **[measured]** Note that at `r = 13` the
*denominator* overflows too (`1932053504` ≠ `13! = 6227020800`), which the study does not mention.

`A(0)`: `unsigned count = 2*0 - 1 = 4294967295`, the loop runs ≈2.1×10⁹ iterations and returns

optimisation-level difference. It is worth knowing that removing this loop will make a visible,
harmless ~2 s difference to wall-clock.)

### 2.3 Corrections to the study

**(A) §4.2's "structural" determinism claim mis-identifies the mechanism.** The study says:

> `GiNaC_symbol_set` is `std::set<symbol, std::less<symbol>>`, and GiNaC's `less` orders by
> *serial number* — i.e. by symbol creation order.

This is **wrong for this codebase**. `utilities/GiNaC_utils.h:39-51` specialises
`std::less<GiNaC::symbol>` to order **lexically by name** (`a.get_name() < b.get_name()`), and
`GiNaC_symbol_set` uses that specialisation. Symbol sets are therefore *already* name-ordered, and
`order_symbol_set()` (`GiNaC_utils.cpp:534`) is a redundant re-sort. `canonicalize_loop_labels()`
(`loop_integral.cpp:114`) iterates a `GiNaC_symbol_set` and is consequently deterministic.
**[read]**

The phenomenon the study observed is real, but its causes are different and are given in §3 below.
There *is* one serial-ordered container in the relevant path — `canonicalize_Rayleigh_labels()`
(`loop_integral.cpp:144`) iterates a `GiNaC::exmap`, which is
`std::map<ex, ex, ex_is_less>` and orders by `ex::compare()` (`/opt/local/include/ginac/basic.h:49`,
`ex.h:705`). That is serial/type-dependent, not name-dependent. **[read]**

**(B) "67 lines across 8 files".** The actual Boost surface is **10 files**:
`backends/LSSEFT.{h,cpp}`, `services/argument_cache.{h,cpp}`, `services/symbol_factory.{h,cpp}`,
`utilities/formatter.{h,cpp}`, `instruments/timing_instrument.h`, `shared/error.cpp`, plus
`CMakeLists.txt`. The line count is in the right ballpark and the character of the work is exactly
as described. **[read]**

**(C) "135 filter passes".** 27 registered groups × 5 μ powers = 135, but `main.cpp` *constructs*
29 `Pk_rsd` objects, so **145** filter passes actually execute per element. Immaterial to the
argument. **[read]**

**(D) The `tree-bispectrum` branch is only a partial reference for §7.1(ii).** It fixes
`add_edge` (both directions), keys `unassigned[...]` by `left_mom`/`right_mom`, and converts
`break` → `continue`. But at `contractions.h:555` and `:563` it *still* looks up
`mma_map[clust].find(left_sym)` / `find(right_sym)` — so on that branch the momentum-preference
logic remains dead code as well. The study's prescription ("search and index by `left_mom` /
`right_mom` **throughout**") goes further than the branch does, and its measured
`t1_simple = 678` figure can only be reached by fixing those two lines too. **[read]** Do not
assume the branch can be copied wholesale.

## 3. New finding: GiNaC 1.8.10 randomises expression ordering per process

This is not in the study, it is load-bearing for the whole validation strategy, and it explains a
stronger form of the non-determinism the study reports.

### 3.1 The measurement

A de-Boosted binary was built and run four times with **identical flags**
(`--no-auto-symmetrize --symmetrize-22 --counterterms --output outN`):

| Artefact | Result across 4 identical runs |
|---|---|
| Wall clock | 42.8 s user (matches the study's ~43 s) |
| Kernel count | 101 every time |
| `compute_*` name set | identical every time, **and identical to the 2018 published tree** |
| Sorted set of `double value_ = …` strings | **byte-identical** every time (one md5) |
| Sorted set of `double Wick_ = …` strings | **byte-identical** every time |
| `kernel_integrands.cpp` as a file | **four different md5s** |
| `Pk_expressions.cpp` sorted | **three different md5s** |
| Counterterm map (sorted lines) | **three different md5s** |
| Files differing between two identical runs | **10 of 22** |

So: the *content* is stable, the *naming and ordering* are not. The study reported this for
different builds and for `--counterterms` toggling; it is in fact true of **two consecutive runs of
one binary**. **[measured]**

### 3.2 The root cause

GiNaC 1.8.10 seeds its expression hash from a runtime address, so the hash of a given expression —
and therefore the canonical ordering of `mul`/`add` operands, and therefore the printed form —
changes between processes. Minimal reproduction, run five times:

```
3/7*sin(z)*Pi^(-2)*b*a^4      hash of Pi^(-2) = 1234187412
3/7*sin(z)*b*Pi^(-2)*a^4      hash of Pi^(-2) =  856634517
3/7*sin(z)*Pi^(-2)*b*a^4      hash of Pi^(-2) =  159691924
3/7*sin(z)*Pi^(-2)*b*a^4      hash of Pi^(-2) =  932230292
3/7*Pi^(-2)*sin(z)*b*a^4      hash of Pi^(-2) = 3962746004
```

**[measured]** This is GiNaC's behaviour, not the project's, and it cannot be switched off from
outside the library.

It reaches `LSSEFT-analytic` through a specific, fixable path:

1. `one_loop_element_key::hash()` (`lib/one_loop_reduced_integral.cpp:372-414`) hashes the
   **default-printed strings** of the time function, measure and Wick product.
2. `LSSEFT_impl::LSSEFT_kernel::hash()` (`backends/LSSEFT.cpp:89-121`) hashes the
   **default-printed string** of `(measure*integrand).expand()`.
3. Those hashes are the keys of two `std::unordered_map`s —
   `one_loop_element_db` (`one_loop_reduced_integral.h:211`) and
   `LSSEFT::kernel_db` (`backends/LSSEFT.h:172`).
4. `Pk_rsd_group::visit` (`lib/Pk_rsd.h:176-181`) walks `one_loop_element_db` in bucket order and
   hands elements to `LSSEFT::process_kernels` (`backends/LSSEFT.cpp:498-520`), which assigns
   `ker0, ker1, …` **in that order**.
5. Every emission loop then walks `kernel_db` in bucket order
   (`backends/LSSEFT.cpp:633, 684, 783, 798, 814, 841, 860, 878, 905, 932, 953, 964, 987, 1269, 1290`).

So kernel numbering *and* file ordering are downstream of a per-process-random hash.
`Pk_one_loop_impl::Pk_db` (`lib/Pk_one_loop.h:62`) is a third `unordered_map` in the same family.
**[read]**

Equality is unaffected: `LSSEFT_kernel::is_equal` uses GiNaC structural equality, which is
order-insensitive, so *dedup remains correct*. Only ordering and naming move.

### 3.3 Consequences for the campaign

- Sorting our own containers on a **print-order-independent** key removes causes 1-5 entirely, and
  should give byte-reproducible `autogenerated/` output. Prompt 03 does this.
- It cannot fix ordering *inside* a printed expression where GiNaC's own comparator is consulted
  across operand types. Empirically the `csrc`-printed integrands are stable (4/4 runs) while the
  default-printed counterterm map is not. Prompt 03 must therefore *measure* how far byte-equality
  can be pushed rather than assume it, and record any residue.
- The generated header line `// Generated at <timestamp>` and the whole body of `pipeline_id.cpp`
  are timestamps (`backends/LSSEFT.cpp:619, 1534`). Any byte-comparison must exclude them.
- **The primary regression test must be functional, not textual** — which is what the study's
  Appendix B already says, and now we know precisely why.

## 4. New finding: an unremarked warning in every run

Every run emits, once:

```
warning: Kernel does not depend on available momentum vector q0
```

from `lib/fourier_kernel.cpp:657` (`WARNING_UNUSED_MOMENTA_SING`). It is not mentioned anywhere in
the study. It is presumably benign but it has never been explained, and it is the only diagnostic
the pipeline produces besides the two expected `Empty RSD Pk group for filter pattern 'bG3'` /
`'bG3*b1_1'` messages. It should be captured in the baseline so that a *change* in the warning set
is detectable. **[measured]**

Confirmed absent from a full run: `WARNING_KERNEL_IS_NOT_IR_SAFE`, `WARNING_UNEVALUATED_FABRIKANT`.
**[measured]** — this corroborates study §3.1 and §6.1.

## 5. Independently confirmed: 6 of the 101 emitted integrands are duplicates

Re-parsing all 101 `value_` expressions from a fresh run into SymPy with exact rational literals
(`rationalize` transformation) and reducing with `cancel(together(·))`, keyed jointly on the
`Wick_` string:

```
emitted: 101    distinct after cancel(together): 95
6 duplicate pairs
```

**[measured]** — exactly the study's §3.4 result. (The `kerNNN` labels in the pairs differ from the
study's because of the numbering non-determinism of §3; the pair *structure* is the same.)

This is recorded here as corroboration of the study's method. **Acting on it is out of scope for
this campaign** — changing the dedup key changes the emitted artefact, and the study places that
work in the port, not in the oracle.

## 6. Scope decision for this campaign

The study's own recommendation (§9, Phase −1 and Phase 0) is the scope, and nothing more:

**In scope** — delete Boost; a reproducible build; a differential harness and archived baselines;
determinism; Wick Tier-1 fixes; `A(r)`/`double_factorial`/Legendre-shape hygiene; diagnosis of the
zero-valued Rayleigh rules; tagged pre-fix and post-fix baselines.

**Explicitly out of scope**, per study §9 ("Where to stop") — and therefore *not* to be attempted
by any prompt in this campaign:

- Tier 3: multi-external-momentum Rayleigh reduction, three-or-more `LegP` products, the
  four-Bessel/Levin path, new correlator containers.
- The `Bk` placeholder, three-field blocks, the 12-type cross.
- Replacing the 27 hand-written bias filters with a single polynomial decomposition (§4.2).
- Canonical-form dedup (§3.4), CSE'd emission (§4.3), the IR/asymptotic redesign (§6.2), the IR
  serialisation (§5.1) or the quadrature redesign (§5.3).
- Anything on the SymPy side.

Two judgement calls, recorded so they are not silently revisited:

1. **`is_IR_safe` is left alone.** Study §6 shows it tests the wrong limits and has never fired,
   but §6.2 is written as a specification for the *port*, and §9's Phase −1 list does not include
   it. Touching it would change emitted warnings without improving the oracle's numbers. Prompt 07
   records it in the handover instead.
2. **The 12-type cross is not attempted here.** Study §9 explicitly makes it optional
   ("if it is wanted sooner than the port can deliver it, doing it in C++ first is defensible").
   Nothing in this campaign forecloses it; prompts 04 and 06 are precisely the groundwork it needs.
