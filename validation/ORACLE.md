**Audience:** the author of the Python/SymPy port of `LSSEFT-analytic`. This document assumes you

## 1. What this program is

`LSSEFT-analytic` is a symbolic-computation program (C++ / GiNaC 1.8.10). It does not compute
numbers: it *emits C++ source code* — a 22-file directory called `autogenerated/`, the important
member of which is `kernel_integrands.cpp`, holding **101 one-loop integrand kernels** — which is
then compiled into a separate numerical pipeline elsewhere. The published 2018 reference output is
preserved, unmodified, at `~/Documents/Code/LSSEFT/autogenerated/` (101 kernels, 135 `compute_*`
assembly functions).

Because the program's product is source code, "does the port agree with the oracle?" means "does it
emit the same integrands as *functions*?" — not "does it emit textually identical C++?". §3 explains
why that distinction is load-bearing, not a nicety.

## 2. How to build and run

```bash
./validation/build.sh                 # -> build-validation/LSSEFT_analytic
./validation/run.sh                   # -> validation/out/<UTC timestamp>{,.log}
```

Prerequisites: a C++17 compiler, CMake ≥ 3.16, and GiNaC + CLN discoverable by `pkg-config`
(`pkg-config --modversion ginac` must succeed). **No Boost, no other package-manager step.** That is
itself a campaign result (prompt 01) — the project depended on Boost until 2026-09-04, and Boost was
not installed on the machine the campaign ran on.

`validation/run.sh` invokes the **canonical configuration**, which is what every measurement in this
document and every archived baseline uses:

```bash
./LSSEFT_analytic --no-auto-symmetrize --symmetrize-22 --counterterms --output <dir>
```

**This is not the tool's default.** `--auto-symmetrize` is the default
(`services/argument_cache.h:73`, `auto_symmetrize{true}`), and it costs **~23-26× the wall clock for
identical output** — measured at 19 m 34 s vs 50.9 s on prompt 02's machine, and independently at
19 m 02 s vs 43 s by the feasibility study. Use `--no-auto-symmetrize` (or `run.sh`, which always
does) unless you are specifically testing the symmetrizer. The 2018 published output corresponds to
`auto-symmetrize = 0, symmetrize-22 = 1`, and this is recorded inside **every** generated file as a
comment:

```cpp
// computed using auto-symmetrize = 0, symmetrize-22 = 1
```

(emitted by `backends/LSSEFT.cpp:774`). If you ever see a file without this comment, or with
different values, the run that produced it did not use the canonical configuration.

`main()` exits immediately, before doing any work, unless at least one of `--counterterms`,
`--output`, or `--mathematica-output` is given (`main.cpp:193-194`). If you invoke the binary with
neither flag while debugging something else, it will silently do nothing and exit 0 — this has
wasted time before.

## 3. How to compare — and why it must be functional, not textual

**GiNaC 1.8.10 randomises expression ordering per process.** It seeds its expression hash from a
runtime address, and that hash determines the canonical operand order GiNaC settles on for a given
`add`/`mul` node the first time something forces the hash to be computed. Two runs of the identical
binary with identical flags therefore produce **different** `autogenerated/` trees: the *kernels* are
the same kernels, computing the same integrands, but their names (`ker0`, `ker1`, ...) and their
files' internal ordering differ from run to run — this repository's own `kerNNN` numbering has no
persistent meaning across builds.

Full measurement, causal chain (with file:line anchors) and probe code:
`validation/NONDETERMINISM.md`. Minimal standalone reproduction of the phenomenon itself (not this
project's code, just GiNaC): `validation/ginac_ordering_probe.cpp` — build and run it five times and
watch the hash of `Pi^(-2)` change every time.

**What prompt 03 fixed, and what it did not.** Kernel *naming and file-emission order* are now fully
deterministic — sorted on a print-order-independent canonical key
(`utilities/canonical_print.{h,cpp}`) rather than trusting `unordered_map` bucket order. Five
independent process launches of the same configuration now produce a **byte-identical**
`autogenerated/` tree (21 of 21 non-timestamp files; run `validation/check_determinism.sh` to
reproduce this for yourself). What prompt 03 could **not** fix is GiNaC's own operand order *inside* a
single default-printed expression when GiNaC's own comparator has to arbitrate between operands of
different types — this is why the human-readable counterterm map (the `** COUNTERTERM MAP` console
section under `--counterterms`) still varies textually between runs even though its *content* does
not (see below).

**Use the tooling, not `diff`:**

```bash
python3 validation/compare_autogenerated.py A/autogenerated B/autogenerated
```

This extracts every kernel's `value_` and `Wick_` expression, parses with **exact rational
literals** (SymPy's `rationalize` transformation — critical; see the two traps below), substitutes a
surrogate power spectrum for `data_->Pk(·)`, evaluates each kernel at 25 fixed seeded exact-rational
`(k_, q_, z_)` points in mpmath at 60 digits, and compares the **multisets** of the resulting
25+25-component signature vectors, plus the `compute_*` name sets. Multisets, not per-kernel maps —
so kernel renumbering across builds cannot make the comparison fail, and only a genuine change in
what set of integrands is produced can. Exit 0 = match, 1 = mismatch, 2 = usage/parse error.

Compare against an archived baseline without rebuilding the old code:

```bash
python3 validation/compare_autogenerated.py <fresh>/autogenerated \
    --signatures validation/baselines/pre-fix/signatures.json      # or baselines/post-fix/
```

**The two traps this project's own history hit, and that you will hit too if you are not warned:**

1. **Re-parse with exact rational literals, never default float parsing.** A default float parse of
   an emitted literal like `1.0/30.0` introduces a ~10⁻¹⁶ relative residual against the true rational
   `1/30`. That residual is *below* double precision and looks exactly like a real disagreement
   between two kernels when it is nothing of the sort. `validation/canonical_form.py`'s
   `parse_exact()` uses SymPy's `rationalize` transformation for this reason; if you write your own
   comparison tooling in the port, do the same or you will spend time chasing phantom mismatches.
2. **Compare multisets of signatures, never per-kernel name-to-name mappings.** Kernel numbering is
   **not** stable across code changes, even after prompt 03's determinism fix — the sort key depends
   on the kernel's own printed content, so any change that alters how a kernel prints (even one that
   changes no value at all — the FabJ closed-form change, `5e2b208`, is exactly this) permutes the
   numbering. `ker42` in one tree has no necessary relationship to `ker42` in another. Only "does this
   *set* of 101 integrands, as functions, match that *set*" is a meaningful question.

**The dedup diagnostic is a different tool for a different question:**

```bash
python3 validation/canonical_form.py --dedup validation/out/<run>/autogenerated
```

reduces each `value_` via `cancel(together(·))` and reports algebraically distinct kernels: currently
**101 emitted, 95 distinct, 6 duplicate pairs** (issue I-05, §5). This is a diagnostic, not the
regression gate — the regression gate is `compare_autogenerated.py`.

**The counterterm map** (the `** COUNTERTERM MAP` section of `--counterterms` output) needs its own
comparison mode, because its *raw* text varies run to run for the reason given above (I-10, §5):

```bash
python3 validation/canonical_form.py --counterterm-map <run>.log
```

recursively canonicalises the print order of every commutative `*`/`+`/`-` operand list and
normalises leading signs — purely textual, no algebra — and gives a single md5 across every run this
campaign ever measured, including `--auto-symmetrize`: `1c177140d3688e558b445609f8c585a4`.

## 4. What the oracle is verified to be right about

*(Study §3.1, corroborated by measurement where noted; file:line references are current as of
`baseline/post-fix`, commit `74bc2849d715cfe358451420b290cf1e73c5f74a`.)*

- **The μ decomposition into {0, 2, 4, 6, 8} is complete.** Max μ degree is exactly 8; every odd
  coefficient is identically zero. **[measured, prompt 02]**
- **The 27 registered bias filter groups are complete.** 29 distinct bias monomials exist;
  `main.cpp` constructs 29 `Pk_rsd` objects and registers 27; the two omitted (`bG3`, `b1_1·bG3`)
  cancel to zero, and the code warns about exactly those two, every run. **[measured, prompt 02]**
- **The only three-Bessel integral the reduction can ever produce is `FabJ(0, n, n)`.** The angular
  integral over the Rayleigh vector is always performed first, against a kernel with no angular
  dependence on it, so only the ℓ = 0 mode of the plane-wave expansion survives
  (`one_loop_reduced_integral::one_loop_reduce_one_Rayleigh`). That family has the elementary closed
  form
  ```
  FabJ(0, n, n; s, t, u) = π / (4 s t u) · Pₙ( (t² + u² − s²) / (2 t u) )
  ```
  valid for **every** `n`, and is evaluated this way in `lib/detail/special_functions.cpp` (commit
  `5e2b208`), replacing a hand-written table that was only valid for `n ≤ 4` and threw a warning
  outside that range (never observed to fire on the current operator basis). The `λ ≠ 0` and
  `μ ≠ ν` cases in `FabJ_eval` are **precondition assertions**, not gaps in a table — say this
  plainly if you re-derive this integral in the port. See the corrected feasibility study §3.1 and
  `~/Documents/Code/ScaleDependentBias/documents/LEGACY-CODE-AUDIT.md` §1.3, §4.2 for the full
  derivation of why no other three-Bessel integral can arise.
- **All 101 emitted integrands are IR-finite as q → 0.** (Note: `is_IR_safe()` does not itself
  establish this correctly for every limit — see I-06 below. This claim is about the actual emitted
  integrands, confirmed independently during planning, not about that function's own logic.)
- **The Wick connectivity test is correct** for two legs, and, after prompt 04's fix, for any number
  of legs (`graph::add_edge`/`is_connected` in `lib/detail/contractions.cpp`).
- **`auto_symmetrize` does not change the physics.** Measured: identical 101/101 functional
  signatures, identical counterterm map, for ~23-26× the cost. Its emitted *text* differs
  substantially (80 of 101 `value_` lines, 53 of 101 `Wick_` lines) — the symmetrizer builds
  differently-ordered but algebraically identical expression trees — which is exactly the case that
  demonstrates why the comparison must be functional.

## 5. Known limitations this campaign deliberately did not address

Each with its issue ID (from `prompts/pre-python-migration-fixes/IMPLEMENTATION_STATE.md`) and the
study section that specifies the fix. None of these was fixed here because fixing any of them would
change the emitted artefact this oracle exists to hold fixed — see `RECONCILIATION.md` §6 for the
scope boundary. **The port should treat all of them as real work items, not settled questions.**

- **I-05 — 6 of the 101 emitted integrands are exact algebraic duplicates** that the emitter's
  string-hash-based dedup key misses; `cancel(together(·))` gives 95 distinct kernels
  (`validation/canonical_form.py --dedup`). Confirmed on every archived tree, pre-fix and post-fix,
  and on the 2018 published tree, with the same pair *structure* (the `kerNNN` labels in each pair
  differ between trees because numbering is not stable — see §3). Study §3.4. **The port should make
  a rational normal form the dedup key**, not the printed-string hash this codebase uses.
- **I-06 — `is_IR_safe()` (`backends/LSSEFT.cpp:435-461`, called as a warning only at `:757`) tests
  the wrong limits.** It Taylor-expands about `q → 0` and `x → 0` in each integration variable; it
  never tests the collinear corner `q → k, x → 1`, where six of the 22-type integrands genuinely go
  as `R⁻²`. It is per-kernel, so it cannot see cancellations *between* kernels, and it has never
  fired in any run this campaign measured. Study §6.
- **I-09 — the `8π²` normalisation applied at `backends/LSSEFT.cpp:793`
  (`kernel.print_integrand(subs_map, 8*GiNaC::Pi*GiNaC::Pi)`) is invisible in the emitted code.** It
  is applied silently as a print-time argument, not written into any emitted line. **If the port
  drops it, every downstream result will be rescaled by 8π² and nothing in the emitted C++ will tell
  you.** Study §5.2.
- **The 13-type Wick product has `Pk(k)` stripped** by `print_WickProduct`'s filter
  (`backends/LSSEFT.cpp`, the `print_WickProduct` function) and reinstated as `Ptr_init` in the
  numerical assembly, which is why the 13/22 large-scale-flow cancellation is performed *numerically*
  downstream rather than analytically inside this oracle. Study §6.1.
- **Tier 2 heuristics that are exact only for the two-point function:**
  `assign_external_momenta`'s `labels.size() > 2` skip (`lib/detail/contractions.h:377` — note the
  adjacent comment says "more than one", the code tests "more than two"; the two disagree, and the
  unassigned set has been measured at size exactly 1 across 780 calls in a full run, so neither
  branch has ever actually fired) and `assign_loop_momenta`'s greedy first-fit
  (`lib/detail/contractions.h:407-470`, the `find_candidate` lambda). Study §7.1(iv)-(v) specifies a
  spanning-tree replacement for the port.
- **Tier 2 combinatorics:** `enumerate_contractions` builds all `(N−1)!!` pairings and filters for
  connectedness afterwards — 15 pairings for six fields, 945 for ten, 135135 for fourteen. Study
  §7.1(vi).
- **Tier 3, all of it:** multi-external-momentum Rayleigh reduction
  (`ERROR_TOO_MANY_KEXT_IN_RAYLEIGH`, `ERROR_KEXT_HAS_WRONG_COEFF_IN_RAYLEIGH`), three-or-more `LegP`
  products (`ERROR_CANT_INTEGRATE_MORE_THAN_TWO_LEGP`), two simultaneous Rayleigh momenta
  (`ERROR_MULTIPLE_RAYLEIGH_MOMENTA_NOT_IMPLEMENTED` — structural for the two-point function, a
  genuine barrier for `B222`-type bispectrum terms), new correlator containers. Study §7.1 Tier 3 as
  revised 2026-09-05 — **the study's original "four-Bessel integral" claim for this tier was
  withdrawn**; §4 above explains why every term the one-Rayleigh reducer *accepts* yields
  `FabJ(0,n,n)`. A term with two simultaneous Rayleigh momenta is refused at
  `lib/one_loop_reduced_integral.cpp:556`, not reduced: `B222`-type and higher-loop topologies
  need a fresh derivation or the invariant numerical route, and this family says nothing about them.
- **No `Bk` placeholder anywhere** in the symbolic core; `enumerate_contractions` rejects an odd
  field count outright. Study §7.1 "Blocks of three".
- **Two recovery branches in `evaluate_Wick_contractions`** (for a contraction with one unassigned
  endpoint) remain written but **unexercised** even after prompt 04's fix activated 678 other
  previously-dead branches — they are exactly what an *n*-point function or a three-block case would
  need, and they have never been run. Do not assume they are correct merely because they compile.
- **I-02 — every run emits** `warning: Kernel does not depend on available momentum vector q0`
  (`lib/fourier_kernel.cpp:657`). **Unexplained.** Presumed benign; captured in both baselines
  (`validation/baselines/{pre,post}-fix/warnings.txt`) so a change is detectable. Investigate only if
  it changes.
- **I-10 — toggling `--counterterms` still perturbs GiNaC's own intra-expression print order**
  (not content) relative to a `--no-counterterms` run of the identical binary, even though two
  same-flags runs are now byte-identical (prompt 03 closed that case). Functionally identical either
  way (confirmed: 101/101 matched, `compute_*` identical). Out of scope — the canonical invocation
  this whole document is built around always uses the same flags.

## 6. Rayleigh momenta — what the port must reproduce

*(Source: `validation/RAYLEIGH-ZERO-FINDINGS.md` §§3, 8, and the corrected
`~/Documents/Code/ScaleDependentBias/documents/LEGACY-CODE-AUDIT.md` §1.3. This is the part of this
document a port author most needs, and the campaign spent an entire prompt plus a day of follow-up
work getting the diagnosis right — the first diagnosis, on 2026-09-04, was wrong, and it is worth
understanding *why* it was wrong, not just the corrected conclusion.)*

**What a Rayleigh label is.** It is a device that keeps a non-rotationally-invariant denominator
`1/|Q|²` symbolic, for some vector `Q` built from the kernel's own momenta, until the numerator has
been reduced. Only three call sites mint labels: `alpha`, `beta` and `InverseLaplacian`
(`SPT/one_loop_kernels.cpp`, `lib/fourier_kernel.h`), plus a Wick-product fallback in
`match_Wick_to_Rayleigh` (`lib/loop_integral.cpp:185`). A label always appears in `K` with a
**negative even power** — `simplify_mul` (`utilities/GiNaC_utils.cpp:198`) throws
`ERROR_RAYLEIGH_MOMENTA_POSITIVE_POWER` on a matched positive power — and numerators are always
written in the underlying momenta, never in the label. This asymmetry (label only in denominators,
numerator in the real momenta) is the single fact everything else in this section follows from.

**The reduction's integration order is forced, and this is why only `FabJ(0,n,n)` arises.**
Rayleigh direction is integrated first (only the ℓ = 0 mode survives), plane-wave direction second,
loop direction last. A port must either keep this order or re-derive the reduction from scratch —
changing it is not a safe refactor. This is why §4's `FabJ(0,n,n)` claim holds for every term the
one-Rayleigh reducer accepts, whatever the operator basis, not just empirically on the current one.

**Zero-valued Rayleigh rules are the normal, safe signature of a `P13`-type self-contraction —
not a defect, and the campaign spent real effort getting to this understanding.** Every canonical run
produces exactly 128 Rayleigh rules whose value collapses to zero, all arising inside
`Pk_one_loop::cross_product` when a Wick contraction self-contracts two of a single third-order
kernel's own linear legs against each other, pinning them to equal-and-opposite loop momentum — the
code's representation of `F₃(L, −L, k)`. In that configuration an SPT vertex like `alpha(k₁₂, k₃)`
with `k₁₂ = 0` is formally `0/0`: its denominator vanishes, but so does its numerator, because
numerators are always written in the underlying momenta and vanish identically when the labelled
vector does. **The whole term is identically zero, not singular**, and the Rayleigh label's job is
exactly to stop GiNaC evaluating `pow(0, -2)` and throwing `power::eval(): division by zero` before
that cancellation has had a chance to happen.

**The trap the first diagnosis (2026-09-04) fell into, and why it matters for a port:** testing
"does the zero-valued label's symbol still occur in `K`" looked, at first, like it *failed* in 92 of
128 cases — i.e. the label was still syntactically present in an apparently-nonzero-coefficient term.
The correct explanation took another day to find: at that point `K` is still in **indexed** form
(`(L.i)²`, `(L.j)⁻²`, ... with dummy tensor indices), and GiNaC's indexed algebra is *not* a normal
form — `simplify_indexed` and `.normal()` do **not** cancel `(L.i)² · (L.j)⁻²` down to `1` when the
two dummy indices differ, even though the underlying scalar identity `|L|²/|L|² = 1` obviously holds.
So a term can sit in `K` with a literally nonzero GiNaC coefficient and still be identically zero as
a function of the momenta. The cancellation only becomes visible at
`dot_products_to_cos(K).expand()` — the first statement of the `one_loop_reduced_integral`
constructor — which rewrites every `(L.i)²` as the scalar `L·L` and every contracted pair as a
`Cos(·,·)`, after which ordinary polynomial `expand()` sees the cancellation and removes it. Checked
at that point, and only at that point, **zero of the 128 labels survive**, and the invariant the
study originally proposed — *a zero-valued rule's label never occurs in the kernel it multiplies* —
holds exactly.

**What this means for a port, stated as two rules:**

1. **Reduce every term to scalar form (or otherwise canonicalise `|L|²`-type factors) *before*
   testing whether it is nonzero, or whether a given label is "in use".** Testing on an indexed
   representation will show phantom survivors that are not real — this is exactly the mistake this
   campaign made and then corrected.
2. **Never substitute a zero value directly into a label that carries a negative power.**
   `remove_Rayleigh_trivial`'s existing pruning mechanism works by substitution, and substituting
   `label → 0` into a factor like `pow(indexed(label, i), -2)` makes GiNaC throw
   `power::eval(): division by zero` (verified directly with a standalone GiNaC test). Zero-valued
   rules are harmless sitting in the rule list — the reduction's own selection logic
   (`term.has(sym)`) simply never selects them once the scalar-form check above has passed — but they
   must be *dropped from the list after the check*, never *substituted*.

The assertion that encodes rule 1 (`ERROR_RAYLEIGH_ZERO_LABEL_SURVIVES`) lives in the
`one_loop_reduced_integral` constructor, immediately after
`K = dot_products_to_cos(K).expand()`. It never fires on the current operator basis (verified:
emitted tree byte-identical with and without it) and is a safety net for the port to notice if this
assumption is ever violated, not evidence that it will be.

**One further constraint worth restating explicitly:** a Rayleigh momentum's value must be
`±L ± k` for exactly one external momentum `k`; the kernel may carry at most two Legendre factors in
the loop direction, at most one of which is partnered with `k`. An **unlabelled** non-rotationally-
invariant denominator is *not* detected by anything in this pipeline and will produce either a GiNaC
pole error or silently wrong output — there is no assertion protecting against an unlabelled hazard,
only against a labelled one whose value should have been provably zero.
