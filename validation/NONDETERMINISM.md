# Non-determinism in `LSSEFT-analytic`'s emitted output

**Measured:** 4 September 2026
**Code state:** `pre-python-migration-fixes/02-oracle-harness-and-baseline`, binary built from
`d8d4532` (prompt 01's tip)
**Toolchain:** Apple clang 21.0.0, arm64-apple-darwin25.5.0, GiNaC 1.8.10 + CLN 1.3.7 (MacPorts),
CMake 3.31.11 Release, macOS 26.5.2, Apple M1 Pro
**Produced by:** `prompts/pre-python-migration-fixes/02-oracle-harness-and-baseline.md`, work item 3

---

## The one-sentence version

Two runs of the same binary, with identical flags, produce **different** `autogenerated/` trees:
the *content* of the emitted integrands is stable to the byte, but the *naming and ordering* are
not, because both are downstream of a GiNaC expression hash that is seeded from a runtime address
and therefore differs from process to process.

This document is the evidence for issue **I-01** and the input to prompt 03. It is deliberately
precise about which artefacts are stable and which are not, because prompt 03's job is to move
artefacts from the second list to the first, and it needs to know what "done" looks like.

Every unstable file names kernels; no stable file does. The instability is not diffuse — it is
entirely the kernel naming and ordering of §4, and nothing else.

### 3.2 The counterterm map

| Run | md5 of the sorted `** COUNTERTERM MAP` section |
|---|---|
| 1 | `d823cbc01617bca5adc401aaa50144dc` |
| 2 | `fa8869a80b3303128b9904f5aca32444` |
| 3 | `6101b518f5b6814d1492026dda78cb54` |
| 4 | `fa8869a80b3303128b9904f5aca32444` |
| 5 | `e41060737aa90f05195b6a2d8659a809` |

**Four distinct md5s in five runs** (planning saw three in four runs; runs 2 and 4 collided).
Number of differing sorted lines against run 1, out of 760: run 2 → 16, run 3 → 62, run 4 → 16,
run 5 → 62.

**Sorting the lines does not canonicalise this map.** That is a new measurement and it matters for
prompt 03. The variability is *inside* each line, not in the order of the lines: the label multiset
(`-- <bias>`, `@ k^n`, `-> mu^n`) is identical across all five runs (md5
`37e9884e73a65cfa92ad75a19831ca35`), the line count is 760 every time, and 478 entries are `= 0`
every time. What moves is GiNaC's own operand ordering within a default-printed expression, e.g.
run 1 vs run 2:

```
run1:  -> mu^0 = -1/30*(56*DE(z)-26*DJ(z)+ ... )*Pi^(-2)*D(z)*Pk(delta,delta,k)*...
run2:  -> mu^0 = -1/30*Pi^(-2)*(56*DE(z)-26*DJ(z)+ ... )*D(z)*Pk(delta,delta,k)*...
```

Identical expression, different printed operand order. This is the residue
`RECONCILIATION.md` §3.3 warns about: it is *not* reachable by sorting our own containers, because
no container of ours is involved.

**It is, however, reachable by canonicalising the print order after the fact.**
`validation/canonical_form.py --counterterm-map <run.log>` recursively sorts the operands of every
commutative `*` and every `+`/`-` term list and normalises leading signs — a purely textual
transformation, no algebra, no re-parsing. Measured:

| Run | md5 of the print-order-canonicalised map |
|---|---|
| 1 | `1c177140d3688e558b445609f8c585a4` |
| 2 | `1c177140d3688e558b445609f8c585a4` |
| 3 | `1c177140d3688e558b445609f8c585a4` |
| 4 | `1c177140d3688e558b445609f8c585a4` |
| 5 | `1c177140d3688e558b445609f8c585a4` |
| `--auto-symmetrize` (§8) | `1c177140d3688e558b445609f8c585a4` |

**One md5 across six independent processes.** So the counterterm map's *content* is stable, and the
whole of the run-to-run variation in it is commutative reordering — nothing more. That is a much
stronger statement than "the label multiset is stable", and it is the useful input to prompt 03:

- the emitted counterterm map is not byte-stable and probably cannot be made so from outside GiNaC;
- but it **is** verifiably content-stable, so a regression test on it can be built today, and
  `validation/baselines/pre-fix/counterterm-map.canonical.txt` is the reference form;
- prompt 03 should compare the canonicalised form and record the byte-level residue, not promise
  byte-equality.

The canonicaliser does **no algebra** by design: it will not see through distribution, `2*a` vs
`a+a`, a factor moved in or out of a bracket, or a change of exponent form. A real change to the
counterterm map must still show up as a difference.

`validation/baselines/pre-fix/counterterm-map.sorted-lines.txt` preserves the raw sorted-lines
artefact, clearly labelled as unusable for comparison, because that is the thing prompt 03 has to
make byte-stable.

### 3.3 Not a source of variation: the 2018 tree

For completeness, because it is easy to misread: the sorted `value_`/`Wick_` md5s of the five 2026
runs (`772fdcf3…`, `c5e5f54e…`) differ from those of the 2018 published tree
(`dab3c903…`, `bcbcfac8…`). That is a *different* effect — a 2018 GiNaC printing the same
expressions with different intra-expression operand order — and it is precisely why the regression
test compares functions rather than text. Functionally the two trees are identical: see
`validation/README.md` and the prompt-02 log for the 101/101 signature match.

## 4. Root cause

Reproduced from `RECONCILIATION.md` §3.2, which established it; the file:line anchors below are
that document's, not re-derived here.

GiNaC 1.8.10 seeds its expression hash from a runtime address. The hash of a given expression —
and therefore the canonical ordering of `mul`/`add` operands, and therefore the printed form —
changes between processes. It reaches this project by a specific, and partly fixable, path:

1. `one_loop_element_key::hash()` — `lib/one_loop_reduced_integral.cpp:372-414` — hashes the
   **default-printed strings** of the time function, the measure and the Wick product.
2. `LSSEFT_impl::LSSEFT_kernel::hash()` — `backends/LSSEFT.cpp:89-121` — hashes the
   **default-printed string** of `(measure*integrand).expand()`.
3. Those hashes are the keys of two `std::unordered_map`s:
   `one_loop_element_db` (`lib/one_loop_reduced_integral.h:211`) and
   `LSSEFT::kernel_db` (`backends/LSSEFT.h:172`).
   `Pk_one_loop_impl::Pk_db` (`lib/Pk_one_loop.h:62`) is a third map in the same family.
4. `Pk_rsd_group::visit` (`lib/Pk_rsd.h:176-181`) walks `one_loop_element_db` in **bucket order**
   and hands elements to `LSSEFT::process_kernels` (`backends/LSSEFT.cpp:498-520`), which assigns
   `ker0, ker1, …` in that order.
5. Every emission loop then walks `kernel_db` in bucket order — `backends/LSSEFT.cpp:633, 684, 783,
   798, 814, 841, 860, 878, 905, 932, 953, 964, 987, 1269, 1290`.

So kernel numbering *and* file ordering are both downstream of a per-process-random hash.

**Equality is unaffected.** `LSSEFT_kernel::is_equal` uses GiNaC structural equality, which is
order-insensitive, so dedup remains correct. Only ordering and naming move. This is why the
functional signature multiset is stable while ten files are not.

Two further sites must be excluded from any byte-comparison for an unrelated reason: the generated
`// Generated at <timestamp>` header line and the whole body of `pipeline_id.cpp`
(`backends/LSSEFT.cpp:619, 1534`) are timestamps.

### What prompt 03 can and cannot reach

- **Reachable:** causes 1–5. Sorting our own containers on a key that does not depend on print
  order removes kernel-numbering and emission-order variation entirely, and should make the
  `autogenerated/` tree byte-reproducible modulo the two timestamp sites.
- **Not reachable from outside GiNaC:** the intra-expression operand ordering of a
  *default-printed* expression, which is what §3.2 measures in the counterterm map. Note the
  contrast: the `csrc`-printed integrands are stable 5/5 (§2) while the default-printed counterterm
  map is not (§3.2).

## 5. Warning set

Identical in all five runs, and archived at `validation/baselines/pre-fix/warnings.txt`:

```
warning: lsseft-analytic : Kernel does not depend on available momentum vector q0
warning: lsseft-analytic : Empty RSD Pk group for filter pattern 'bG3'
warning: lsseft-analytic : Empty RSD Pk group for filter pattern 'bG3*b1_1'
```

The first is issue **I-02**: emitted once per run from `lib/fourier_kernel.cpp:657`
(`WARNING_UNUSED_MOMENTA_SING`), never explained anywhere in the study, presumed benign. It is
captured here so that a *change* in the warning set is detectable. The other two are expected: 29
`Pk_rsd` groups are constructed but `Pk_bG3` and `Pk_b1_1_bG3` are not registered
(`main.cpp:415-506`).

Absent from every run, as expected: `WARNING_KERNEL_IS_NOT_IR_SAFE`, `WARNING_UNEVALUATED_FABRIKANT`.

## 6. The minimal GiNaC reproduction

`validation/ginac_ordering_probe.cpp` is a ten-line program with no dependency on this project. It
exists so that a future reader does not blame `LSSEFT-analytic` for a library behaviour, and so
that the check can be repeated cheaply after a GiNaC upgrade.

```bash
c++ -std=c++17 -O2 $(pkg-config --cflags ginac) validation/ginac_ordering_probe.cpp \
    -o /tmp/ginac_ordering_probe $(pkg-config --libs ginac)
for i in 1 2 3 4 5; do /tmp/ginac_ordering_probe; done
```

Measured, GiNaC 1.8.10, five consecutive runs:

```
3/7*sin(z)*b*Pi^(-2)*a^4      hash of Pi^(-2) =  690959509
3/7*sin(z)*b*Pi^(-2)*a^4      hash of Pi^(-2) = 2795615381
3/7*sin(z)*Pi^(-2)*b*a^4      hash of Pi^(-2) = 2638984341
3/7*Pi^(-2)*sin(z)*b*a^4      hash of Pi^(-2) = 2939794580
3/7*sin(z)*Pi^(-2)*b*a^4      hash of Pi^(-2) = 1766438036
```

Three distinct orderings in five runs and a different hash every run — the same result planning
obtained (`RECONCILIATION.md` §3.2), with different hash values, which is itself the point.

**If a future GiNaC prints the same line five times with the same hash**, the upstream behaviour has
changed and prompt 03's workaround should be revisited.

## 7. Consequences for validation

1. **`diff` on the generated tree is not a regression test.** Ten of 22 files differ between two
   identical runs. Anyone who tries it will drown in false positives and stop trusting the test.
2. **The regression test must be functional.** `validation/compare_autogenerated.py` compares
   multisets of signature vectors, which is insensitive to both kernel renumbering and GiNaC term
   order. That is the gate; everything in this document is why.
3. **Stable auxiliary keys**, usable today as cheap secondary checks: the sorted `value_` set, the
   sorted `Wick_` set, the `compute_*` name set, the warning set, and the print-order-canonicalised
   counterterm map (`canonical_form.py --counterterm-map`).
4. **Unstable, do not gate on these until prompt 03 lands:** any per-file md5, and the *sorted*
   counterterm map.
5. **Always exclude** the `// Generated at` header line and `pipeline_id.cpp` from any byte
   comparison.

## 8. `--auto-symmetrize`: the same answer, 25× slower

The study measured the default `--auto-symmetrize` path at 19 m 02 s against 43 s with identical
counterterm maps, and planning deliberately did not repeat the 19-minute run. It was repeated here.

```bash
./build-validation/LSSEFT_analytic --auto-symmetrize --symmetrize-22 --counterterms --output <dir>
```

| | canonical (`--no-auto-symmetrize`) | `--auto-symmetrize` | ratio |
|---|---|---|---|
| Wall clock | 50.94 s | **1173.91 s** = 19 m 34 s | **23.0×** |
| User CPU | 45.31 s | **1113.58 s** = 18 m 34 s | **24.6×** |
| Peak RSS | 34,963,456 B | 125,370,368 B | 3.6× |
| Kernels emitted | 101 | 101 | — |
| `compute_*` names | 135 | 135 | — |
| Warning set | the 3 of §5 | the same 3 | — |
| Counterterm map, print-order canonicalised | `1c177140…` | `1c177140…` | **identical** |
| Functional signature multiset | — | **101 of 101 matched, exact key, `compute_*` identical** | **identical** |

The study's claim is confirmed with a measured number: **identical output for ~25× the cost.**

One detail worth recording, because it is a good illustration of why the gate is functional. The
`--auto-symmetrize` tree's emitted *text* is substantially different: **80 of the 101 sorted
`double value_` lines and 53 of the 101 `double Wick_` lines differ** from the canonical run, and
the md5 of the sorted `value_` set is `b3f0d70799a62d493c0a876620bac3eb` against the canonical
`772fdcf3d57d620b0fe9548b738dbc52`. Every one of the 101 signatures nevertheless matched on the
*exact* key. Note that this text difference is **not** the per-process effect of §3: the five
canonical runs all agreed on that md5, so the symmetrizer is building genuinely differently-ordered
expression trees, deterministically, that happen to be algebraically identical.

A `diff`-based test would have reported ~130 changed integrand lines here. The correct answer is
"no change".
